# 并行编排工具调研与可适配逻辑

> 日期：2026-11-13
> 调研范围：Codex 生态为主，另取 Claude Code 官方并行能力、Conductor、Paradev（原 Superset）、Vibe Kanban、Crystal/Nimbalyst 中「有独特机制」的部分
> 方法：官网与仓库原文优先；社区帖子仅作旁证并标注
> 性质：**只调研与登记，不改代码、不改第四轮清单**
> 局限：Tavily 额度用尽改用 AnySearch/DeepSeek；未安装实测任何工具，以下均为文档与源码阅读结论

## 0. 结论先行

1. **最值得参考的是 `codex-supervisor-mcp`**。它和 Threadweave 解决同一个问题（多 worker 并行改一个仓库），但把「派单、记账、验收、恢复、落地、清理」全部从模型上下文下沉到了工具契约。它的 SKILL.md 与 Threadweave 的 SKILL.md 可以逐条对照。
2. **Claude Code 官方文档提供了两条 Threadweave 缺的硬规则**：`.worktreeinclude`（把 gitignored 文件带进每个 worktree）和「worktree 无法验证时绝不降级为无隔离运行」。
3. **Conductor 提供了一个 Threadweave 完全没有的决策维度**：不是所有并行都要拆 worktree。独立交付 → 多 workspace；共享分支/上下文（实现+review、前后端必须一起 land）→ 同一 workspace 多 agent。
4. **不建议整体替换形态**。Threadweave 的差异化是「Codex 原生线程可对话、可读、可归档」，`codex-supervisor-mcp` 用的是 `codex exec` 子进程，两者不可互换。正确做法是**学机制、保留形态**。
5. 工具生命周期本身是风险信号：Vibe Kanban（28.7k stars）已宣布 sunsetting，Crystal 改名 Nimbalyst，Superset 改名 Paradev。**把工作流绑在协议 + 本地脚本上，比绑在单一商业工具上更抗变化**——这一点反而印证了 Threadweave 当前的形态选择。

## 2. `codex-supervisor-mcp` 机制拆解（最同构）

### 2.1 与 Threadweave 的定位差异

| 维度 | Threadweave | codex-supervisor-mcp |
| --- | --- | --- |
| 执行载体 | Codex 原生线程（`create_thread`） | `codex exec` 子进程 |
| 主线程能否与 worker 对话 | 能（`send_message_to_thread`） | 不能直接对话，只能 `ask_codex_worker` 走只读旁路 |
| 状态存储 | `.threadweave/<run>/state.json` | `supervisor.sqlite` + `events.jsonl` |
| 编排者 | 模型按 `SKILL.md` 执行 | MCP 工具强制契约 |
| 跨客户端 | 仅 Codex | 任意 MCP 客户端（Claude Code、Codex 等） |
| 可观测性 | 状态文件 + 线程 | SQLite 台账 + 网页看板 + 原始 JSONL |

**判断**：它牺牲了「与 worker 实时对话」的能力，换来了「编排不可绕过」。Threadweave 不能照搬，但可以把其中可独立成立的检查下沉。

### 2.2 可直接借鉴的九条机制

| # | 机制 | 它怎么做 | Threadweave 现状 |
| --- | --- | --- | --- |
| S1 | 派单前写集冲突预留 | `ownedPaths` 必填，两个 worker 写入范围有交集直接拒绝；预留与任务入库在同一事务 | 无；第四轮 O03 只在集成前检查 |
| S2 | 独立验收 | `acceptance` 由 supervisor 在 worker 退出后**独立执行**；`verification` 只是 worker 自报跑过的命令 | `integrate(verification)` 只是一个字符串，无独立执行语义 |
| S3 | `failed` / `lost` 分离 | 非零退出、`turn.failed` 记 `failed`；被外部信号杀掉、运行进程失踪记 `lost`，用 `resume` 接回 | 只有 `failed`，无法区分「任务失败」与「进程消失」 |
| S4 | 失败归因枚举 | `failure.source` 区分 provider / supervisor_process / workspace_setup / model_output / acceptance / worker_process | `errors[]` 为自由结构，无分类 |
| S5 | 环境准备前置 | `workspaceSetup` 支持 `links`（复用 `node_modules`）、`submodules`、`commands`（如 `nuxi prepare`）；缺 setup 直接返回 `workspace_setup_required` | 只有 300 秒初始化预算，无准备阶段与依赖链接 |
| S6 | preflight contract | 先跑同环境 probe，拿到 `preflight_id`；base/sandbox/setup/命令任一变化必须重跑 | preflight 一次性、无 ID、无失效条件 |
| S7 | 上下文闸门 | `overview` 封顶 7000 字节；事件读取有 `limit` / `maxChars` / `kinds`；`overview_delta` 只返回游标之后的变化 | 只有定性的 Context Economy，无量化预算 |
| S8 | 三段交付状态 | `verified`（验收通过）≠ `landed`（合入本地）≠ `push_verified`（远端可验证） | 只有 `merged` 一个结果 |
| S9 | 三级清理 | `SAFE` / `REVIEW` / `BLOCKED`；SAFE 要求验收通过 + 远端已验证 + 干净 + 无活跃进程；执行前重验 fingerprint 与远端 SHA | `cleanup.py` 已有分类，但无「远端已验证」这一档 |

### 2.3 它的两条「反直觉但正确」的规则

1. **worker 不提交，主线程代提交**。`workspace-write` 沙箱里 `.git` 是只读的，worker 根本 commit 不了。它的做法是接受这个边界：worker 只改代码，`land_codex_worker(commitMessage)` 由主线程提交并 cherry-pick。Threadweave 要求 worker 自己 commit，在同类沙箱下会直接失败。
2. **`exit_code: 0` 不等于完成**。完成证据是 acceptance + diff，不是退出码，也不是 worker 的自我汇报。

## 3. Claude Code 官方：两条硬规则 + 一套边界经验

### 3.1 `.worktreeinclude`：gitignored 文件注入

官方文档明确：worktree 是 fresh checkout，需要初始化开发环境；要自动把 `.env` 等 gitignored 文件带进每个新 worktree，用 `.worktreeinclude`。

**对 Threadweave 的价值**：真实项目里 worker 启动失败的第一大原因不是代码问题，而是缺 `.env`、本地配置、证书、`node_modules`。Threadweave 目前完全没有这一层，worker 只能靠自己发现并手动补。

### 3.2 worktree 无法验证时，绝不静默降级

Claude Code 的 resume 失败分类极其明确：

| 情况 | 行为 |
| --- | --- |
| worktree 目录已删除 | 提示后清除绑定，在无隔离目录继续 |
| 无法验证 worktree | 保留绑定，本次无隔离继续，下次 resume 重试 |
| 拒绝使用该 worktree | 清除绑定，明确报出拒绝原因 |
| 无法重新进入 | 保留绑定，报出修复方法 |

关键点：在 headless/Agent SDK 模式下，除「目录已删除」外**全部直接报错退出**，并通过 `startup_failure_reason`（`worktree_unverified` / `worktree_resume_refused`）让调用方分支处理，**不会静默降级到无隔离目录继续跑**。

**对 Threadweave 的价值**：`recovery.py` 已有 `revalidate` / `block`，但没有写成「绝不降级」的硬不变量。这条应该显式写进 `SKILL.md`。

### 3.3 agent teams 的边界（已被验证的共识）

Claude Code 的 agent teams 目前是实验性功能，其限制清单与 Threadweave 的规则高度重合：

| Claude Code 限制 | Threadweave 对应规则 |
| --- | --- |
| 无嵌套 team，只有 lead 能管理 | worker 不得自行派生 worker |
| lead 固定，不能转移 | leader 是当前会话，不转移 |
| task 状态会滞后，阻塞依赖任务 | 完成判定必须验证报告路径 + commit SHA，不信任状态标签 |
| 无法恢复 in-process teammates | 替换后新 attempt 重过启动门禁 |

这说明 Threadweave 的这几条不是过度设计，而是当前所有实现都会撞上的共同约束。

## 4. Conductor：一个 Threadweave 缺的决策维度

Conductor 官方概念页给出的判断标准：

| 任务形状 | 选择 | 原因 |
| --- | --- | --- |
| 两个功能可以独立发布 | 多 workspace | 各自分支、运行状态、PR 路径 |
| 一个功能需要「实现 + 修测试」 | **同一 workspace** | 需要同一分支和最新改动 |
| 多个 issue 并行探索 | 多 workspace | 可独立归档/合并/丢弃 |
| 一个分支需要第二意见 | **同一 workspace** | review 意见要落在同一 diff 上 |
| 高风险实验可能丢弃 | 多 workspace | 与主线隔离 |

**对 Threadweave 的价值**：Threadweave 当前是「一 worker 一 worktree」的硬规则。但真实场景里，「前端后端必须一起 land」「实现者 + 审查者看同一 diff」这类任务，拆成两个 worktree 反而增加合并成本——因为它们的价值恰恰来自共享同一份代码状态。

这不是说 Threadweave 的隔离错了，而是说它**只覆盖了一半场景**。补法有两种：
- 低成本：在 `SKILL.md` 阶段 1 增加「同分支协作」判定，明确这类任务**不进入 Threadweave**，由单线程或 subagent 完成；
- 高成本：新增 `shared-workspace` 模式（多 agent 同分支，靠角色分工而非隔离）。

社区还有一条观察（未在官方文档确认）：Conductor 只并行「footprint 不重叠」的 spec，重叠的自动串行化。如果属实，这与 S1 的写集预留是同一思路的产品化。

## 5. 形态与生命周期：三条事实

1. **Vibe Kanban 官网首行写着「Vibe Kanban is sunsetting」，项目转社区维护**。它有 28.7k stars，仍然停了。
2. **Crystal 的继任者是 Nimbalyst**；**Superset 已改名 Paradev**。两个都是「换名/换壳继续」。
3. **`codex-supervisor-mcp` 只有 3 stars、273 commits**，但设计文档完整度远高于多数同类项目。

结论：**star 数不是选型依据，机制是否可验证才是**。同时，任何绑定单一商业工具的工作流都有被停服的风险；Threadweave 以协议 + 本地脚本为主体，抗变化能力更强，这一点应当在「是否投入」的判断里计入正面因素。

## 6. 可适配逻辑清单

分三档：**A 直接补强**（低风险、小改动）、**B 需要设计**（中等成本）、**C 扩展形态**（战略性）。

### A 档：直接补强

#### A1 · 派发前写集冲突预留（强化 O03）

- **来源**：`codex-supervisor-mcp` 的 `ownedPaths`。
- **机制**：`ownedPaths` 必填，两个 worker 的写入范围有交集时**在派单阶段直接拒绝**；预留与任务入库在同一事务；运行时有 guard 拦直接写；`land` 时再查完整 diff。三层检查的位置不同、目的不同。
- **Threadweave 现状**：O03 只计划了「集成前对比 diff」，发现太晚。
- **适配建议**：把 O03 改为两级——
  1. 派发前：`ownedPaths` 两两求交集，非空即拒绝派发（glob 展开到文件级再比，避免 `src/*` 与 `src/a.py` 的假阴性）；
  2. 集成前：`git diff --name-only base..head` 必须落在 `ownedPaths ∪ scopeExceptions` 内。
- **成本**：在 O03 基础上 +2 小时。
- **注意**：它自己也承认「声明脚本仍可能产生清单外副作用」，所以这**不是文件系统沙箱**，不能当作安全边界宣传。

#### A2 · acceptance 与 verification 分离（强化 O01/O02）

- **来源**：`codex-supervisor-mcp` 的 `acceptance` / `verification` 二分。
- **机制**：`acceptance` 是派单时写死的验收命令，由 supervisor 在 worker 退出后**独立执行**；`verification` 只是 worker 自报跑过的命令与退出码，不作为完成证据。
- **Threadweave 现状**：`controller.integrate(role, attempt, merge_commit, verification)` 的 `verification` 只是一个字符串，由 leader 传入，没有「独立执行」的语义；worker 报告里的测试结果可能被直接当成证据。
- **适配建议**：O01 的 `verify.json` 明确定义为「由 leader 独立执行的验收计划」；worker 自报的测试结果降级为 `selfReportedVerification`，与 `acceptance` 分开记录。`integrate` 要求 `acceptance` 通过，而不是要求 `verification` 字段非空。
- **成本**：在 O01/O02 基础上 +半天。

#### A3 · `failed` / `lost` 分离，`lost` 走 resume 而不是 recreate

- **来源**：`codex-supervisor-mcp` 状态机（`failed` vs `lost`）。
- **机制**：非零退出、`turn.failed`、spawn 失败 → `failed`；被外部信号杀掉、运行进程失踪、行写了但进程从未起来 → `lost`；`lost` 用 `resume_codex_worker` 接回同一会话，worktree、改动、`thread_id` 都保留。
- **Threadweave 现状**：worker 状态只有 `failed`，`recovery.py` 对「thread 不存在」返回 `recreate`，会新建 attempt + 新分支 + 新 worktree，丢掉已有改动。
- **适配建议**：`WORKER_TRANSITIONS` 增加 `lost`；`recovery.classify_worker_recovery` 增加 `resume` 动作（当 thread 仍存在、worktree 仍存在、branch 未变时）；只有 thread 真不存在才 `recreate`。
- **成本**：半天（含状态表、schema、恢复分类、测试）。
- **价值**：这是当前恢复路径里最贵的一次浪费——已有改动被整条丢弃。

#### A4 · `failure.source` 归因枚举

- **来源**：`codex-supervisor-mcp` 的 `failure.source` / `failure.code`。
- **机制**：区分 provider（模型不可用）、supervisor_process、workspace_setup、model_output（报告不合 schema）、acceptance（验收失败）、worker_process（进程异常）。
- **Threadweave 现状**：`state.errors[]` 为自由结构，恢复时只能靠人读 message。
- **适配建议**：`errors[]` 的每项增加 `source` 枚举；`recovery.py` 按 source 决定动作（如 provider → block 并上报；workspace_setup → 重跑 setup；model_output → 要求重发报告；acceptance → 返工）。
- **成本**：2–3 小时（不改变现有错误文本）。

#### A5 · `.worktreeinclude` 式 gitignored 文件注入（并入 O06）

- **来源**：Claude Code 官方 worktree 文档。
- **机制**：`.worktreeinclude` 列出需要复制到每个新 worktree 的 gitignored 文件（`.env`、本地配置等）。
- **Threadweave 现状**：worktree 是干净 checkout，worker 常因缺 `.env` 或依赖目录而启动失败；`startup_gate` 还要求 `status_porcelain` 为空，worker 连补文件都不敢。
- **适配建议**：O06 增加 `worktreeInclude` 配置（文件列表 + 目标路径），由 leader 在创建 worktree 后、启动核验前复制；复制后这些文件必须在 exclude 或 gitignore 内，避免污染 `status_porcelain`。
- **成本**：并入 O06，+2 小时。

#### A6 · preflight_id 与 contract 失效

- **来源**：`codex-supervisor-mcp` 的 `preflight_codex_worker` / `get_worker_preflight`。
- **机制**：先跑同 workspace / base / sandbox / guard 的短 probe，全部 probe 命令实际执行通过才 `passed`；`create` 时带 `preflight_id`；base、sandbox、setup、`ownedPaths`、命令、context 任一变化必须重跑。
- **Threadweave 现状**：preflight 是 leader 一次性执行的环境检查，没有 ID、没有失效条件；多 worker 时无法证明「每个 worker 的环境与其 preflight 一致」。
- **适配建议**：preflight 结果记 `preflightId` + `contractHash`（对 base/sandbox/setup/ownedPaths 做规范化哈希）；`create_worker` 与 `dispatch` 校验 `preflightId` 未过期；任一契约字段变化即失效。
- **成本**：1 天。**建议与 O06 一起做**，否则 setup 变了但 preflight 没过期，会出现假通过。

#### A7 · overview 预算与读取闸门（强化 O02）

- **来源**：`codex-supervisor-mcp` 的 `get_orchestration_overview`（封顶 7000 字节）与事件读取 `limit` / `maxChars` / `kinds`。
- **机制**：状态总览有硬字节上限；事件读取默认截断并提示 `truncated`；`overview_delta` 只返回游标之后的变化，不返回全量历史。
- **Threadweave 现状**：Context Economy 只有定性要求（「消息只带信号」「`read_thread` 是昂贵的兜底」），没有预算数值，也没有 delta 读取。
- **适配建议**：O02 的 `report.json` 增加 `maxBytes` 约束；`threadweave.py status` 增加 `--compact`（封顶字节）与 `--since <cursor>`（只返回变化）；`run_log` 增加游标语义。
- **成本**：在 O02 基础上 +半天。

#### A8 · 三段交付状态（verified / landed / push_verified）

- **来源**：`codex-supervisor-mcp` 的交付状态分离。
- **机制**：验收通过 = `verified`；合入本地集成分支 = `landed`；远端分支确实包含该提交 = `push_verified`。三者互不等价。
- **Threadweave 现状**：`integrationLog` 只有 `merged`，容易被读成「已交付」。
- **适配建议**：`integrationLog` 增加 `delivery` 字段（`verified` / `landed` / `pushVerified`）；默认停在 `landed`；只有用户明确要求推送且远端 SHA 核对通过才置 `pushVerified`。这与用户「只提交不推送」的约束天然一致。
- **成本**：2 小时。

### B 档：需要设计

#### B1 · `rebaseOnto`：worktree 落后主线时的接续

- **来源**：`codex-supervisor-mcp` 的 `resume_codex_worker({rebaseOnto: "HEAD"})`。
- **机制**：把 worker worktree 挪到主线新头——stash、跳过已合入补丁、重放新增提交、放回；冲突原样退回，不起 worker。
- **Threadweave 现状**：只校验 `baseIsAncestor`，worktree 落后时没有标准动作，只能让 worker 自己 rebase 或 leader 手工处理。
- **适配建议**：新增 `scripts/rebase.py`，封装上述四步，并在 `recovery` 中增加 `rebase` 动作。
- **成本**：1–2 天。**风险**：自动 rebase 与「不自动改动用户工作」的原则冲突，必须默认 dry-run + 显式确认。

#### B2 · 上下文 capsule 与 candidate/verified fact

- **来源**：`codex-supervisor-mcp` 的 context capsule 与 fact 状态机。
- **机制**：新派单/resume 只注入 L0（身份、任务、依赖摘要、路径/SHA 命中的 verified facts）；完整事件、diff、历史报告、candidate facts 不自动注入；fact 只有 acceptance 通过后才从 candidate 升为 verified；base SHA 或 watched path 变化后自动过期。
- **Threadweave 现状**：消息只带信号、大内容走文件，方向一致；但没有「事实是否已验证」「事实何时过期」的概念。
- **适配建议**：给 `state.json` 增加 `facts[]`（`status: candidate|verified|expired`、`baseSha`、`watchedPaths`）；派发时只注入 verified facts；集成成功后把该 worker 的报告升为 verified。
- **成本**：2–3 天。**前提**：先在真实 run 里观察「旧结论被复用导致返工」的频率，否则是过度设计。

#### B3 · SAFE / REVIEW / BLOCKED 三级清理（强化现有 cleanup）

- **来源**：`codex-supervisor-mcp` 的 cleanup plan。
- **机制**：三档分类；SAFE 要求 acceptance 通过 + `push_verified` + worktree 干净 + 无活跃进程/依赖 + Git 注册与路径归属可证明；`apply` 前重验 fingerprint 并 fetch remote 再验 landed SHA；branch、task row、event、JSONL、artifact 永远保留。
- **Threadweave 现状**：`cleanup.py` 已有 `protect_*` / `remove` 分类，但没有「远端已验证」这一档，也没有 apply 前的二次重验。
- **适配建议**：把现有动作归并为三级；`remove` 前必须重新采集观察值（避免用过期证据删除）；分支与报告永久保留。
- **成本**：半天到 1 天。

### C 档：扩展形态

#### C1 · 四种 `workspaceKind`

- **来源**：`codex-supervisor-mcp`。
- **四种形态**：`git_worktree`（默认）、`read_only_in_place`（只读分析）、`scratch`（联网研究，不写原目录）、`in_place_write`（显式授权的非 Git 写入）。
- **Threadweave 现状**：假定所有 worker 都在 git worktree 里改代码。
- **适配建议**：至少支持 `read_only` worker——真实场景里「一个 worker 审查设计、一个 worker 写实现」很常见，只读 worker 不需要 worktree，也不需要合并。`scratch` 与 `in_place_write` 风险高，暂不做。
- **成本**：2–3 天（要改隔离门禁、报告与清理逻辑）。

#### C2 · 同 workspace 多 agent 模式

- **来源**：Conductor 的 parallel-agents 决策表。
- **机制**：共享分支/上下文的任务（实现 + review、前后端必须一起 land）放在同一 workspace，多 agent 协作，不隔离。
- **Threadweave 现状**：硬性「一 worker 一 worktree」。
- **适配建议**：短期只在 `SKILL.md` 阶段 1 增加判定——这类任务**不进入 Threadweave**，改走单线程或 subagent；长期再评估是否需要 `shared-workspace` 模式。
- **成本**：短期 2 小时（文档）；长期 1–2 周（新模式）。

## 8. 不建议适配

| 方向 | 理由 |
| --- | --- |
| 39 个工具的全套 API | 大部分是它自身形态（MCP + 子进程 + SQLite）的产物，Threadweave 用原生线程，不需要等价映射 |
| SQLite 台账 | `state.json` 在当前规模足够；引入数据库会破坏「零依赖、可直接读」的优势 |
| 网页看板 | 当前瓶颈是协议在真实项目上跑不通，不是状态不可见；O04 的 `next` 命令性价比高得多 |
| 自动 push / 自动部署 | 与用户「只提交不推送」的约束直接冲突 |
| 自动恢复一次 `lost` / `no_work` / `invalid_report` | 与 Threadweave「超时不等于已停止」「不盲重试」的原则冲突；应保留人工确认 |
| 完整文件系统沙箱 | 对方明确说明不是沙箱；Threadweave 也不应把 `ownedPaths` 宣传成安全边界 |

## 9. 对 Threadweave 定位的启示

1. **学机制，不换形态。** `codex-supervisor-mcp` 用 MCP 换来了「编排不可绕过」，代价是失去与 worker 的实时对话。Threadweave 的 `send_message_to_thread` 能中途纠偏、`read_thread` 能查真实上下文，这是子进程形态给不了的。不要在这一点上妥协。
2. **但要承认「协议不可强制」是真实短板。** 第四条结论不是「改成 MCP」，而是「把**检查**下沉，把**判断**留在模型」。A 档八条全部符合这个标准：它们是确定性检查，不涉及取舍。
3. **原生线程的成本必须被计量。** 上下文是 Threadweave 最贵的资源，而 `overview` 7000 字节上限、`delta` 读取、报告 JSON 侧车这些手段，恰好都是为「原生线程 + 大上下文」设计的补丁。这比新增功能更值得做。
4. **如果要产品化，MCP 是被验证过的形态**（`codex-supervisor-mcp` 与 Paradev 都有 MCP server）。但那属于上一份文档里的路径 B/C，不是当前阶段。
