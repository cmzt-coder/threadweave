# Threadweave 生产力插件评估

日期：2026-11-17。评估对象：Threadweave `0.1.0`，当前提交 `5953a37`。结论：它可以作为 **Codex 高级用户/内部团队的工程协作 skill** 试用，但还不是面向普通用户的即装即用生产力插件。

## 一、项目实际形态

Threadweave 不是一个独立桌面应用，也不是带完整插件清单的传统插件。当前由三部分组成：

- `SKILL.md`：Codex 读取的 leader 工作流与护栏；
- `agents/openai.yaml`：Codex skill 的显示名称、描述和默认提示；
- `scripts/`：36 个 Python 辅助模块，负责状态、控制器、Git、桥接、报告、恢复、验收和清理；
- `tests/`：46 个 smoke 测试套件，当前共 1466 项断言。

安装方式是把仓库克隆到：

```text
${CODEX_HOME:-$HOME/.codex}/skills/threadweave
```

然后重启 Codex。它不是普通 Web 服务，也没有 Web UI、数据库服务或独立守护进程。

## 二、适合的能力

### 优势

- 把真实 Codex thread 作为 worker，而不是临时 subagent；
- 每个 worker 有独立分支和 worktree，避免共享 checkout；
- 有 leader 状态文件、恢复和替换协议；
- 强调串行合并、逐分支验收和最终集成复查；
- 明确禁止无授权推送、强制删除和静默模型替换；
- 对失败、停滞、丢回执、范围越界和清理已有本地门禁；
- 大量本地测试，状态和证据文件可审计；
- 适合长时间、可拆分、需要过程纪律的工程任务。

### 适合的任务

- 一个 API、一个前端页面和独立测试可以并行开发；
- 多个模块写入集基本不重叠；
- 共享契约可以由 leader 事先冻结；
- 任务需要多个分支、报告、串行合并和反复验证；
- 使用团队希望保留完整操作证据和恢复记录。

### 不适合的任务

- 小改动或一两个小文件修改；
- 多个 worker 必须同时修改同一核心模块；
- 非 Git 项目或无法提供独立 worktree；
- 普通业务用户需要“点一下就能用”的界面；
- 宿主不开放真实 thread、wait、worktree 或附件能力；
- 只需要一次性问答或简单代码生成的任务。

## 三、当前生产力评估

| 维度 | 评估 | 说明 |
| --- | --- | --- |
| 工作流设计 | 较强 | 有 preflight、启动门禁、状态机、串行集成和最终复查 |
| 故障防护 | 较强 | 未授权、漂移、活动 worktree、停止证据缺失等大多 fail-closed |
| 本地测试 | 较强 | 46 套 smoke / 1466 项断言 |
| 真实宿主可靠性 | 中等 | 仍有 thread cwd/primary、附件身份、模型保持和 wait 能力边界 |
| 安装体验 | 中等偏弱 | 需要 clone 到 skills 目录并重启 Codex |
| 普通用户可用性 | 较弱 | 术语多、流程长、需要理解 Git/worktree/thread |
| 产品化程度 | 较弱 | 无独立 UI、无统一 run/status/resume 产品入口 |
| 维护成本 | 中等偏高 | 高度依赖 Codex 工具语义和版本变化 |

## 四、是否可作为生产力插件使用

### 可以作为

作为 **Codex 原生 skill** 在以下前提内使用：

- 使用者是开发者或熟悉 Codex 的高级用户；
- 项目已注册为 Codex Git 项目；
- 当前宿主支持真实 thread/worktree 工具；
- 用户愿意在首次运行时确认拆分、模型、分支和授权；
- 团队接受首次设置和最终审查成本。

### 暂不建议作为

- 面向普通用户的一键式插件；
- 公开发布后承诺“安装即自动完成并行开发”的产品；
- 不允许创建真实线程的宿主；
- 对不可逆资源清理要求完全自动化的生产环境。

## 五、距离生产级插件的主要差距

1. **缺少标准产品入口**：目前主要靠 `$threadweave` skill 提示和 Python 辅助命令，没有一个统一的 `run/status/resume/cleanup` 用户界面。
2. **缺少交付包装**：仓库没有 `pyproject.toml`、`package.json` 或独立插件包 manifest，主要通过 skills 目录安装。
3. **宿主能力耦合强**：thread、worktree、附件、模型和清理语义随 Codex 版本变化，兼容层仍需维护。
4. **真实故障矩阵未完全闭环**：O16 仍有宿主签名身份、shared/protected/submodule 和预归档授权端到端验收缺口。
5. **首次使用成本高**：preflight、项目登记、worktree、模型配置、消息授权和清理概念较多。
6. **H01/P0 仍有真实环境缺口**：迁移后模型保持、附件观察、多 projectId、create timeout 和 wait 缺失尚未完全验证。
7. **文档量很大**：已有大量阶段验收记录，对新用户来说需要一份更短的产品化入口文档。

## 六、建议的生产化路线

### P0：先做成可靠的内部技能

- 保持默认严格门禁；
- 固化 Codex 版本兼容矩阵；
- 提供一键 `doctor`，检查 thread/worktree/model/project 能力；
- 将 O16 剩余项转为版本化外部验收清单；
- 统一状态查看和恢复命令。

### P1：做成可安装的内部插件包

- 增加标准版本、安装和升级说明；
- 统一 skill、脚本和模板的入口；
- 增加最小示例仓库与 5 分钟快速开始；
- 为 leader 提供结构化状态看板或 CLI 摘要；
- 将 worker 模板、报告格式和清理流程版本化。

### P2：再考虑对外产品化

- 做面向非专家的配置向导；
- 提供宿主能力自动探测和降级；
- 增加可视化运行状态、任务树和阻塞面板；
- 完成真实 shared/protected/submodule、多 projectId、create timeout 和模型保持验收；
- 明确隐私、权限、审计和删除授权模型。

## 七、最终判断

### 推荐定位

> **Codex 高级工程协作 skill / 内部生产力工具**，而不是现阶段的通用商业插件。

### 推荐试用方式

先在一个非关键、可回滚的 Git 仓库中，用 2 个边界清晰的 worker 完成一次小型任务：

- API/后端与前端分离；
- 测试/文档独立；
- 不共享写集；
- 串行合并；
- 保留报告和清理证据。

### 暂不推荐

- 直接用于无人值守的生产发布；
- 自动推送或自动删除 worktree；
- 让普通用户不经过确认直接创建多个 worker；
- 在宿主能力未验证时承诺“全自动并行开发”。

## 结论

Threadweave 已经具备一个高质量 Codex 工程协作 skill 的骨架和大量护栏，适合内部开发团队试用。它的核心价值是**流程纪律和隔离**，不是“开更多线程”本身。

但以当前状态，它还不能被称为成熟的通用生产力插件。最合理的定位是先作为“Codex 高级用户的并行工程工作流”，完成宿主兼容和产品入口收敛后，再决定是否产品化。
