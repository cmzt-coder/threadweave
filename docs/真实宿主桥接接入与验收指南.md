# 真实宿主桥接接入与验收指南

日期：2026-11-13。用户已确认 A 路线：由当前桌面 leader 桥接真实 Codex 工具。第一阶段验证线程查询；第二阶段按用户指定的 `deepseek-flash · high` 完成单 worker 创建和消息往返。

## 当前完成范围

`DesktopBridgeAdapter` 保持 HostAdapter 的只读 `read_thread` 能力。`DesktopWriteBridgeAdapter` 增加显式配置的 create_worker、send_message；创建默认仍关闭，必须提供 model/thinking/title/既有基线 ref。控制器先生成持久请求，leader 领取后执行工具并回填，控制器从磁盘回读结果。`state.md` 是 `state.json` 的派生视图，不能反向驱动状态。

Python 不直接连接桌面私有 socket，不启动 daemon，不隐式调用模型。创建和消息由 leader 执行真实桌面工具，Python 只管理账本和回执。wait/worktree/会话归档仍由 leader 独立执行，尚无对应适配器方法；双 worker 完整验收未完成，T06 保持部分完成。

## 文件与状态契约

| 文件 | 用途 |
| --- | --- |
| `scripts/desktop_bridge.py` | 查询/创建/消息请求账本、HostAdapter 和操作 CLI |
| `scripts/controller.py` | `observe_worker_host`：绑定检查与持久化观察 |
| `scripts/state_view.py` | 从已校验的 state.json 重建 state.md |
| `.threadweave/<run>/bridge/<operation>.json` | 每次操作的请求、领取与结果；按 run/operation 隔离 |
| `.threadweave/<run>/state.json` | 控制器运行状态与已接收的最小宿主观察 |
| `.threadweave/<run>/state.md` | 对人可读的历史状态视图 |
| `.threadweave/<run>/reports/` | leader 保全的原始工具响应及回填材料 |

请求绑定 run、operationId、role、attempt、taskRevision 和规范化请求 SHA256，参数纳入哈希。白名单为 `mcp__codex_app__read_thread`、`mcp__codex_app__create_thread`、`mcp__codex_app__send_message_to_thread`。只读查询参数固定 local、turnLimit=1、includeOutputs=false、maxOutputCharsPerItem=400；只有最小线程身份与状态进入 hostObservation。

状态流：`pending → in_flight → succeeded/failed`。领取产生唯一 claimToken 并在外部调用前持久化。同一操作只能领取一次；不同请求不能复用 operationId。结果关联不符、不同终态结果覆盖、未来时间或非最小元数据均拒绝。

进程中断后，`in_flight` 不会自动变回 pending，也不会自动调用宿主。leader 可显式标为 `unknown`；原调用结果找到后，必须附核对依据才能完成。找不到结果时保留未决，不猜测成功/失败、不自动重发。需要再次只读查询时，由 leader 明确决定并使用新的 operationId，旧记录保留。

响应哈希、请求哈希及 claimToken 用于完整性和误关联检查，不是宿主签名，也不能证明回填者身份。leader 是可信执行边界；原始响应的来源与内容需由其核对。不得把手写的成功 JSON 当成真实宿主证据。

## 新的只读操作如何执行

前提：run 已有通过 schema 校验的 state.json，目标 threadId 已登记在对应 worker 中，且当前用户授权覆盖该查询。此阶段尚无通用 run 初始化命令；本次探针的 run 由 leader 显式登记，不能复制示例占位 ID 冒充真实线程。

1. 用 `observe --run <run> --operation <新 ID> --role <role> --attempt <attempt>` 调用控制器。没有结果时退出码为 3，打印 pending，并先写入请求；这不表示工具已执行。
2. 用 `inspect` 核对操作、绑定身份及最小参数，再执行 `claim`。仅 pending 可领取；领取成功也不等于工具执行成功。
3. leader 在当前桌面会话使用领取记录中的固定工具及参数，调用真实 `read_thread`。CLI 不会替 leader 发起调用。
4. 保存真实工具返回，核对实际返回 thread.id/hostId；保留原始状态，例如 `notLoaded`，不能自行改成 idle。工具错误记录为失败；通信结果不确定则保留 in_flight/unknown。
5. leader 生成最小回填对象，使用 `complete --response <file>` 提交。成功对象必须有 runId、operationId、requestSha、claimToken、method、source=desktop_tool_bridge、observedAt、status=succeeded、toolResultSha、metadata；metadata 仅含 threadId、hostId=local、status。失败对象用 error 替代 metadata。
6. 再执行同一 `observe`，控制器核对 run/role/attempt/taskRevision/threadId，保存宿主观察并生成 state.md。未决时仍退出 3；错误退出 2；接收成功退出 0。

单次观察不会推进 worker 状态，不会刷新工作进展 lastObservation，也不会写入停止证据或 acceptance。任何后续派发、停止确认、独立验收与清理都需要它们各自的最新证据。

## 第二阶段：创建和消息契约

创建请求只接受 project + worktree + 显式既有 branch/ref 的目标，不自动从默认分支创建基线，也不把本地未提交改动带入 worker。model、thinking、title、prompt 必填；宿主不接受模型时记录实际错误，禁止替换模型再试。模型可用性仍以实际宿主校验为准，本地账本不维护易失效的模型白名单。

创建成功回执的 metadata 只允许 `threadId/hostId` 或 `clientThreadId/hostId` 二者之一。后者只说明异步创建已受理；`create_worker` 继续抛出 BridgePending，不能把 client ID 当 threadId 发消息。leader 核对唯一 project/title、完整初始 prompt、创建时间和分配目录，并保存真实读取证据；核对模型配置与独立 Git 基线后，通过 `resolve-creation` 回填真实 ID 和核对依据。当前桌面列表没有直接返回 client→thread 映射，所以这里保留 leader 审核边界，不能宣称由宿主提供了签名关联。零匹配或多匹配时保持未决，禁止猜测或重建线程。

`creationResolution` 记录原 client ID、实际 threadId、local、projectId、title、model、thinking、基线 branchName、cwd、observedAt、toolResultSha、evidence，并单独计算 SHA256。此处 branchName 是创建起点 ref，不是后续 worker 工作分支。核对结果不可覆盖，相同结果重放不写盘。回执中的 succeeded 只表示 create 工具返回成功，不表示 worktree 已 ready 或启动门禁通过。

消息请求仅接受 local、threadId、prompt，不允许临时模型覆盖。成功回执只允许 status=accepted，不能当作完成、停止或验收证据。`Controller.dispatch` 在发送前持久化启动证据及 `dispatchIntent.bridgeOperationId`；排队抛 HostActionPending 时保留 pending，worker 仍为 ready。已有 pending/unknown intent 阻止再次 dispatch。

真实回执落盘后，使用同一 run/role/attempt/taskRevision/operationId 执行 `resume-dispatch`：只读既存消息账本，核对 threadId、消息内容与绑定，然后推进 dispatched、递增 activityRevision。它不会调用 send_message，也不会为不存在的操作生成请求。停止中的 worker、终端 run、错误任务版本和落后 revision 均拒绝恢复。

```bash
# 参数、消息和回填文件由 leader 根据已确认配置及真实返回生成。
python3 scripts/desktop_bridge.py prepare-create \
  --repo . --run <run> --operation <create-id> --role <role> \
  --params <creation-params.json>

python3 scripts/desktop_bridge.py resolve-creation \
  --repo . --run <run> --operation <create-id> --resolution <resolution.json>

python3 scripts/desktop_bridge.py prepare-send \
  --repo . --run <run> --operation <message-id> --role <role> \
  --thread <real-thread-id> --message-file <message.txt>

# 正式派发应先走 Controller.dispatch；prepare-send 仅准备独立控制消息，
# 不代替启动门禁、dispatchIntent 或正式派发授权。
python3 scripts/desktop_bridge.py resume-dispatch \
  --repo . --run <run> --operation <formal-message-id> --role <role>
```

领取、原始工具执行、unknown 核对和 complete 步骤沿用前文；每个动作使用独立 operationId。CLI 不执行这些工具，参数导出所依据的是桌面工具 schema，不是 App Server 的 ThreadStartParams。
