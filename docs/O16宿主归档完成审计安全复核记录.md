# O16 宿主归档完成审计安全复核记录

日期：2026-11-16。复核对象：`2c093bf` 引入的 `scripts/host_archive_guard.py` 及其记录。结论：其“完成观察”逻辑可以保留，但原输出对调用者连续性、批准和宿主保护存在过度声明，必须收紧；收紧后仍不能作为清理授权。

## 复核发现

### F1：不能把 pre/post 附件绑定的 runId 当作调用者连续性

`runId/role/attempt/taskRevision` 能证明两次操作属于同一项目账本绑定，但 `BridgeJournal` 本身没有宿主签名的 calling thread identity。即使前后都通过 `list_artifacts`，也没有字段证明是同一个聊天或同一调用上下文。原 `callerInventoryScopeVerified=true` 容易让后续调用方误以为已证明调用者身份。

修复：改名为 `preInventoryShapeVerified=true`，并新增 `callerContinuityVerified=false`。只读来源映射仍验证清单形状和资源身份，不声称调用者连续性。

### F2：请求哈希不等于批准

原字段 `archiveRequestSha` 只与归档账本请求哈希比较，无法证明该 hash 对应的请求经过用户批准、cleanup plan 指纹复核或停止门禁。把字段称为 approved/通过批准会造成安全误读。

修复：输入字段改为 `expectedArchiveRequestSha`，输出新增 `approvalBindingVerified=false`；本模块只记录请求哈希绑定事实，授权仍由 `managed_cleanup` 和显式操作授权负责。

### F3：`queued` 只能证明受理，不能证明宿主已独立验证保护

历史实证的归档结果只有 `{"type":"queued"}`。后续 `archived_worktree`、目录消失和 Git 注册消失可以证明完成结果，但没有宿主回执字段明确列出 primary/shared/protected 检查结果；工具声明只说明执行时会拒绝这些资源。

修复：保留 `protectionDelegation=host_archive_worktree_execution`，新增 `protectionEnforcementVerified=false` 和 `preObservableProtection=false`。本模块不声称保护已在调用前被观察到，也不声称宿主内部检查可被本项目独立验证。

### F4：完成状态命名应避免被当成清理授权

原 `host_archive_verified` 容易被理解为“整个 O16 已验证”。改为 `host_archive_completion_observed`，并保留 `cleanupEligible=false`、`deletionPerformed=false`。成功 exit code 仅表示完成证据通过，不是后续删除授权。

## 剩余阻塞与下一步

1. 需要定义可验证的调用者连续性证据：必须是宿主或受信任执行上下文提供的身份绑定，不能只靠同一 runId。
2. 需要把归档请求与 cleanup plan 批准、停止证据、Git 计划和授权时刻显式绑定；当前审计器不做这件事。
3. 需要当前宿主真实正向归档和 primary/shared/owner 负向拒绝证据；如果没有真实负向证据，`protectionEnforcementVerified` 必须继续保持 false。
4. O16 继续保持部分完成，不能因为本次收紧而放宽 `execute_managed_cleanup` 的默认门禁。

下一步应设计“调用者连续性 + 批准绑定”的最小证据契约，并明确宿主实际能提供哪些字段；若不能提供，则继续保留 O16 外部阻塞，而不是用本地哈希或 runId 推断身份。
