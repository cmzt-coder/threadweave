## P0 止血（4 条）

### O11 · `failed` / `lost` 分离与 `resume` 恢复

- [ ] **O11 lost/resume 分离**（来源：`codex-supervisor-mcp` 状态机）
- 现状：worker 状态只有 `failed`；`recovery.py` 对「thread 不存在」返回 `recreate`，会新建 attempt + 新分支 + 新 worktree，**把 worker 已有改动整条丢掉**。
- 建议：
  - `WORKER_TRANSITIONS` 增加 `lost`：非零退出、`turn.failed`、spawn 失败记 `failed`；被外部信号杀掉、运行进程失踪、行写了但进程从未起来记 `lost`；
  - `recovery.classify_worker_recovery` 增加 `resume` 动作：thread 仍存在、worktree 仍存在、branch 未变时用 `send_message_to_thread` 接回同一会话；
  - 只有 thread 真不存在才 `recreate`。
- 落点：`scripts/state_store.py`（转换表）、`scripts/recovery.py`、`scripts/controller.py`、`references/state.schema.json`、`references/leader-state-template.md`。
- 验收：
  - `lost` 且 thread/worktree 存在 → `resume`，不改 branch、不新建 attempt；
  - thread 确认不存在 → `recreate`，且保留旧 attempt 审计；
  - `failed` 不因外部信号误判为可恢复；
  - 现有 327 项断言不回归，新增 `lost` 路径单测。
- 成本：0.5 天。依赖：无。
- **为什么是 P0**：当前恢复路径里最贵的一次浪费——已有改动、分支、worktree 全部作废。

### O03 · 写集预留 + 范围漂移两级检查（修订）

- [ ] **O03 写集两级检查**（来源：`codex-supervisor-mcp` 的 `ownedPaths`）
- 现状：协议要求「everything asked, nothing extra」与「files barely overlap」，但只能靠 leader 在合并阶段比对 diff，**发现太晚**。
- 建议：升级为两级——
  1. **派发前**：`ownedPaths` 两两求交集，非空即拒绝派发。glob 先展开到文件级再比较，避免 `src/*` 与 `src/a.py` 的假阴性；
  2. **集成前**：`git diff --name-only <base>..<head>` 必须落在 `ownedPaths ∪ scopeExceptions` 内，否则标 `scope_drift`。
- 落点：新增 `scripts/scope.py`；`controller.dispatch` 派发前调用、`controller.integrate` 集成前调用；派发模板增加 `ownedPaths` 与 `scopeExceptions`。
- 验收：
  - 两 worker 写集有交集 → 派发前报错并列出冲突文件；
  - 写集无交集 → 正常派发；
  - 集成时出现未声明文件 → `scope_drift` 并列出文件；
  - glob 语义显式定义并有单测（测试 `billing/*` 不匹配 `billing/sub/x.py`）；
  - 新增 `tests/scope_smoke.py`。
- 成本：0.5 天（比原 O03 多 2 小时，用于派发前检查）。
- **注意**：这不是文件系统沙箱；声明脚本仍可能产生清单外副作用，不能当作安全边界宣传。

### O01 · 统一验证契约 `verify.json`（修订：acceptance 独立执行）

- [ ] **O01 验证契约**
- 现状：每个 worker 自带验证命令，散落在派发与报告中；`controller.integrate(verification)` 的 `verification` 只是字符串，**worker 自报的测试结果可能被直接当成完成证据**。
- 建议：
  - 阶段 1 由 leader 写 `.threadweave/<run>/verify.json`（步骤、命令、cwd、超时、期望退出码）；
  - **验收由 leader（脚本）在 worker 退出后独立执行**，不采信 worker 自报；
  - worker 自报的测试结果记为 `selfReportedVerification`，与 `acceptance` 分开存；
  - `integrate` 要求 `acceptance` 通过，而不是要求 `verification` 字段非空。
- 落点：新增 `scripts/verify.py`；`controller.integrate` 签名与状态字段调整；`references/worker-dispatch-template.md`、`references/preflight-checklist.md`、`references/state.schema.json`。
- 验收：
  - `python3 scripts/verify.py --plan <path>` 顺序执行并汇总；
  - 任一步非零返回非零，输出失败步骤与 stderr 摘要；
  - 超时步骤被终止并标 `timeout`，不阻塞其余步骤汇总；
  - `acceptance` 未通过时 `integrate` 拒绝；worker 自报通过但 acceptance 失败时以 acceptance 为准；
  - 新增 `tests/verify_smoke.py` 覆盖成功 / 失败 / 超时 / 自报不一致四例。
- 成本：0.5 天。依赖：无。
- **为什么是 P0**：验收证据的来源决定「缺陷可归因」是否成立，这是项目核心价值。

### O05 · `rework` 返工次数上限

- [ ] **O05 返工上限**
- 现状：`controller.rework()` 只执行 `reworkCount += 1`，无上限；worker 连续改不对会无限「返工 → 报告 → 返工」。
- 建议：`state.limits` 增加 `maxReworkPerWorker`（默认 2）；超限后二选一：`replace_worker` 替换，或 leader 接管并记 `leader_takeover`。
- 落点：`controller.rework`、`references/state.schema.json`（`limits` + `workers[].reworkCount`）、`references/leader-state-template.md`。
- 验收：
  - `maxReworkPerWorker=2` 时第 3 次 `rework` 抛错且状态不变；
  - 超限路径留下明确记录（替换或接管，不允许静默继续）；
  - 现有 327 项断言不回归。
- 成本：2 小时。决策点：D1。

### O06 · 环境准备阶段（修订：worktreeInclude + workspaceSetup）

- [ ] **O06 环境准备阶段**
- 现状：`budget.check_initialization` 默认 300 秒，真实 smoke 用时 107 秒是因为仓库零依赖；`npm install` / `poetry install` 常需 5–15 分钟。且 worktree 是干净 checkout，**worker 常因缺 `.env`、本地配置、依赖目录而无法启动**；`startup_gate` 又要求 `status_porcelain` 为空，worker 连补文件都不敢。
- 建议：
  - 新增 `worktreeInclude`：列出需要复制到每个新 worktree 的 gitignored 文件（`.env`、本地配置等），由 leader 在创建 worktree 后、启动核验前复制；复制目标必须在 exclude 或 gitignore 内；
  - 新增 `workspaceSetup{links, submodules, commands}`：`links` 复用主仓库 `node_modules` 等目录，`submodules` 初始化子模块，`commands` 跑 `nuxi prepare` 之类的准备命令；
  - 新增 `state.limits.setupTimeoutSeconds`（默认 900），与 `initializationTimeoutSeconds` 分开计时；
  - `startup_gate` 的 6 项检查不变，证据时效与 `setupTimeoutSeconds` 对齐。
- 落点：`scripts/budget.py`、`scripts/startup_gate.py`、`references/worker-startup-template.md`、`references/worker-dispatch-template.md`、`references/state.schema.json`。
- 验收：
  - 准备命令不在白名单 → 拒绝并给出原因；
  - `setup` 与 `validation` 分别计时，超时判定互不影响；
  - `setup` 后工作区不干净 → 启动门禁失败并列出脏文件；
  - `worktreeInclude` 复制的文件不出现在 `status_porcelain` 中；
  - 未声明 `setup` 的 worker 行为与当前一致。
- 成本：1 天。依赖：无。决策点：D3、D4。
- **为什么是 P1 第一条**：这是「协议在真实项目上跑不起来」的头号原因，且 `.worktreeinclude` 是零成本高收益。

### O02 · 报告侧车 JSON 与机器校验（修订：区分自报与验收）

- [ ] **O02 报告侧车 JSON**
- 现状：`accept_report` 要求 6 个字段，但由 leader 从自由文本提取，无结构校验；leader 需通读 `report.md`。
- 建议：worker 同时产出 `.threadweave/report.json`，字段固定为 `commitSha`、`branch`、`filesChanged[]`、`testsRun[]`、`selfReportedVerification[]`、`contractChanges[]`、`knownRisks[]`；leader 先读 JSON 判断是否接收，需要细节时再读 md。
- 落点：`references/worker-report-template.md`、`controller.accept_report`、`references/state.schema.json` 的 `workers[].report`。
- 验收：
  - 缺 `filesChanged` 时 `accept_report` 抛 `ValueError`；
  - `report.json` 可独立校验，错误给出明确路径；
  - 仅凭 `report.json` 即可完成「接收 / 退回」判断（md 可选）；
  - `selfReportedVerification` 不得被当作 `acceptance` 证据。
- 成本：0.5 天。依赖：O01（`testsRun` 复用 `verify.json` 步骤名）。决策点：D5。

### O12 · `failure.source` 失败归因枚举

- [ ] **O12 失败归因**
- 现状：`state.errors[]` 为自由结构，恢复时只能靠人读 message。
- 建议：每条错误增加 `source` 枚举：`provider` / `supervisor_process` / `workspace_setup` / `model_output` / `acceptance` / `worker_process`；`recovery.py` 按 source 决定动作（provider → block 上报；workspace_setup → 重跑 setup；model_output → 要求重发报告；acceptance → 返工）。
- 落点：`scripts/state_schema.py`、`scripts/recovery.py`、`references/state.schema.json`。
- 验收：
  - 现有错误文本不改，仅新增分类字段；
  - 每类 source 有对应恢复动作的单测；
  - 未分类错误默认 `unknown`，行为与当前一致。
- 成本：3 小时。依赖：无。

### O14 · 三段交付状态

- [ ] **O14 交付状态分离**
- 现状：`integrationLog` 只有 `merged`，容易被读成「已交付」。
- 建议：增加 `delivery` 字段——`verified`（验收通过）、`landed`（合入本地集成分支）、`pushVerified`（远端 SHA 已核对）。默认停在 `landed`；只有用户明确要求推送且远端核对通过才置 `pushVerified`。
- 落点：`scripts/controller.py`（`integrate`）、`references/state.schema.json`、`references/leader-state-template.md`。
- 验收：
  - 默认流程结束后 `delivery=landed`；
  - 未推送时不可能出现 `pushVerified`；
  - 与用户「只提交不推送」约束一致，不引入任何自动推送。
- 成本：2 小时。决策点：D7。

### O16 · 三级清理与 apply 前重验

- [ ] **O16 三级清理**
- 现状：`cleanup.py` 已有 `protect_*` / `remove` 分类，但没有「远端已验证」这一档，也没有 apply 前的二次重验；误删 worktree / 未合并分支不可逆。
- 建议：
  - 归并为三级：`SAFE` / `REVIEW` / `BLOCKED`；
  - SAFE 要求：验收通过 + worktree 干净 + 无未合并提交 + 报告已归档 + 无活跃进程 + 路径归属可证明；
  - `apply` 前重新采集观察值并校验 fingerprint，避免用过期证据删除；
  - branch、报告、事件永久保留。
- 落点：`scripts/cleanup.py`、`scripts/threadweave.py`（`cleanup-plan` 输出三级）、`references/state.schema.json`。
- 验收：
  - 脏 worktree / 未合并分支 / 非本 run 资源 → `BLOCKED`；
  - 证据过期 → `REVIEW`；
  - 只有 `SAFE` 且重验通过才允许 `remove`；
  - 现有清理测试全部保持通过。
- 成本：0.5–1 天。依赖：无。

### O04 · `next` 恢复指令

- [ ] **O04 `next` 恢复指令**
- 现状：`recovery.py` 已能算出 `skip/recreate/block/revalidate/reuse`，但没有命令入口；中断后需人读 `state.md` 与 `state.json` 自行推断。
- 建议：`python3 scripts/threadweave.py next --repo . --run <id>` 输出有序动作清单：需核对的 `dispatchIntent`、需 `resume` / 重验的 worker、建议合并顺序、待清理资源。
- 落点：`scripts/threadweave.py` 增加 `next` 子命令，复用 `recovery.build_recovery_plan`、`state_store.latest_incomplete_run`、`cleanup.build_cleanup_plan`（只读）。
- 验收：

  - `lost` 且 thread 存在 → 输出 `resume`；
  - `complete` 且清理完成 → 「无需动作」；
  - 命令只读：执行前后 `state.json` 内容与 mtime 不变；
  - 新增 `tests/next_smoke.py`。
- 成本：0.5 天。依赖：O11（弱依赖；先做也能用，只是没有 `resume` 动作）。

### O13 · `preflight_id` 与 contract 失效

- [ ] **O13 preflight 契约**
- 现状：preflight 是 leader 一次性环境检查，无 ID、无失效条件；多 worker 时无法证明「每个 worker 环境与其 preflight 一致」。
- 建议：preflight 记 `preflightId` + `contractHash`（对 base / sandbox / setup / ownedPaths 做规范化哈希）；`create_worker` 与 `dispatch` 校验 `preflightId` 未过期；任一契约字段变化即失效。
- 落点：`scripts/controller.py`、`scripts/startup_gate.py`、`references/preflight-checklist.md`、`references/state.schema.json`。
- 验收：
  - 契约未变 → `preflightId` 可复用；
  - base / setup / ownedPaths 任一变化 → 旧 ID 失效并要求重跑；
  - 未提供 `preflightId` 时行为与当前一致（向后兼容）。
- 成本：1 天。依赖：O06（contract 要包含 setup 字段）。

### O15 · overview 预算与 delta 读取

- [ ] **O15 上下文预算**
- 现状：Context Economy 只有定性要求，没有量化预算，也没有增量读取。
- 建议：
  - `threadweave.py status` 增加 `--compact`（总览封顶 7000 字节，参考 `codex-supervisor-mcp` 的实测值）；
  - 增加 `--since <cursor>`，只返回游标之后的状态变化；

- 落点：`scripts/threadweave.py`、`scripts/run_log.py`、`scripts/state_store.py`、`references/state.schema.json`。

  - 不改变 `state.json` 本身的内容。
- 成本：0.5 天。依赖：O02。

### O07 · 序列化资源单点归属

- [ ] **O07 序列化资源归属**
- 现状：`package-lock.json` / `poetry.lock`、迁移文件序号、路由表 / i18n 词条，多 worker 并行时几乎必冲突；当前没有识别机制。
- 建议：项目级配置维护 `serializedPaths`；派发前扫描 `ownedPaths` 是否命中，命中即强制串行——只允许一个 worker 拥有，或要求全部 worker 不改、由 leader 集成后统一生成。
- 落点：`.threadweave/config.json` 或仓库根 `threadweave.config.json`（见 D3）；`scripts/scope.py` 增加检测；派发模板增加「串行资源」声明。
- 验收：
  - 两 worker 同时命中同一 `serializedPaths` → 派发前报错；
  - 单测覆盖 lockfile 与迁移序号两类；
  - 配置缺失时默认空列表，不改变现有行为。
- 成本：0.5 天。依赖：O03 的 path 匹配逻辑。

### O17 · 同 workspace 判定（文档级）

- [ ] **O17 同 workspace 判定**

### O08 · 契约冻结与契约改动检测

- [ ] **O08 契约冻结**
- 现状：「共享契约由 leader 提前定死」仅是文字要求，无机制保证 worker 不私改。
- 建议：leader 派发前把契约文件（OpenAPI 片段 / TS 类型 / migration 头）写入 `.threadweave/<run>/contracts/` 并记 SHA；派发引用该 SHA；集成前校验各分支对契约文件的改动，违规标 `contract_violation`。
- 落点：`scripts/controller.py`、`scripts/archival.py`（复用 SHA256）、`references/worker-dispatch-template.md`。
- 验收：
  - 契约 SHA 不匹配时集成前阻断；
  - worker 私改契约文件被识别并列出差异；
  - 未声明契约的 run 行为不变。
- 成本：1–2 天。前置：项目需存在稳定契约文件，纯脚本类项目不适用。

### O09 · 制品交接（handoff）

- [ ] **O09 制品交接**
- 现状：A 生成中间产物给 B 使用时，若 A 尚未合并，只能通过 leader 转述或提前固定契约。
- 建议：`.threadweave/<run>/handoff/<name>` 存放不可变制品 + SHA；派发携带 SHA；接收方开工前校验。
- 落点：`scripts/archival.py` 扩展或新增 `scripts/handoff.py`；派发模板增加 `handoff` 字段。
- 验收：
  - SHA 不匹配 → 启动门禁拒绝；
  - 已存在同名不同内容 → 抛冲突，不覆盖；
  - 无 handoff 的 run 行为不变。
- 成本：1 天。前置：任务确实存在多阶段依赖。

### O10 · 拆分预演（量化「该不该拆」）

- [ ] **O10 拆分预演**
- 现状：是否需要拆分完全依赖 leader 判断；`SKILL.md` 给了定性校准，但没有量化输入。
- 建议：基于 `git ls-files` 与各 worker 的 `ownedPaths`，计算文件重叠度、目录耦合度、序列化资源命中数，输出风险分与依据。
- 落点：新增 `scripts/split_preview.py`；`SKILL.md` 阶段 1 引用。
- 验收：
  - 输出必须包含计算依据（重叠文件、耦合目录、命中资源），不得只给分数；
  - 标注「仅供参考，不替代 leader 判断」；
  - 在积累 5–10 次真实 run 后再校准权重。
- 成本：2–3 天。前置：真实 run 数据校准。

## 暂不采纳（已评估）

| 方向 | 不采纳理由 |
| --- | --- |
| 多仓库 / 跨仓 monorepo run | 当前前提是「一个仓库根 = 一个 projectId = 一个集成 checkout」；跨仓需重写隔离与合并模型 |
| 全自动合并（无 leader 审查） | 与「缺陷可归因」的核心价值直接冲突 |
| 可视化面板 | 当前瓶颈是协议能否在真实项目跑通，不是状态不可见 |
| 通用调度层 / 多宿主抽象 | 会失去「Codex 原生线程」这一唯一差异化 |
| `codex-supervisor-mcp` 的 39 个工具全套 API | 多数是其形态（MCP + 子进程 + SQLite）的产物，不需要等价映射 |
| SQLite 台账 | `state.json` 在当前规模足够；引入数据库破坏「零依赖、可直接读」 |
| 自动 push / 自动部署 | 与用户「只提交不推送」约束直接冲突 |
| 自动恢复 `lost` / `no_work` / `invalid_report` | 与「超时不等于已停止」「不盲重试」原则冲突，保留人工确认 |
| `rebaseOnto` 自动执行 | 会改动用户工作区；只能做 dry-run + 显式确认，不属于直接集成 |
| 完整文件系统沙箱 | 对方明确说明 `ownedPaths` 不是沙箱；Threadweave 也不应把它宣传为安全边界 |
