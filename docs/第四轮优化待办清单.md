## 第一批：验收可信与返工有界

### O05 · 返工上限与超限阻塞

- [~] **O05**
- 现状：`rework()` 递增 `reworkCount`，没有上限。
- 建议：`limits.maxReworkPerWorker` 默认 2，按 role/attempt 计数；默认超限阻塞该角色，由 leader 决定替换、接管或中止，不自动新建 worker。
- 触发：只有允许返工的当前有效 attempt 才能请求返工；达到上限后拒绝状态转换和任务发送。
- 超限的领域状态与计数保持不变；拒绝原因进入独立审计记录，记录 leader 后续决策。替换仍受停止证据与每角色替换上限约束，不能用新 attempt 绕过 run 预算。
- 落点：`scripts/controller.py`、状态 schema、leader 模板与控制器测试。
- 本地验收：上限为 2 时第 3 次返工拒绝；计数及活动修订不变；无消息发送；旧 attempt、终态或停止中的 worker 不可返工；决策可审计。
- 真实验收：结合 T06 验证一次返工及超限处理，不用 fake adapter 代替真实结果。

### O01 · 独立验收与集成失败阻断

- [~] **O01**
- 现状：验证结果是字符串；当前失败记录不会阻断后续 worker 的集成调用；控制器不执行 Git merge。
- 建议：leader 定义 `.threadweave/<run>/verify.json`，包含契约版本、步骤 ID、命令参数、cwd、超时、期望退出码、依赖及失败处理方式。worker 自报仅保存为 `selfReportedVerification`。
- 独立验收由 leader 控制的执行器采集，需核验 worker 已停止当前写入且任务修订未变化；绑定 run、role、attempt、taskRevision、被测 SHA、工作区身份及验证契约哈希。不得仅接受调用方传入的成功布尔值或任意字符串。
- 区分 worker 分支验收与合入后的集成验收：前者绑定 worker tip；后者绑定合并后的集成 HEAD，并记录集成前后 SHA。SHA、契约或任务修订变化时，相关旧结果失效。
- 明确 Git merge 的执行者、执行目录和只读核验入口。记录 mergeCommit 前核验实际 HEAD、分支归属与祖先关系；写日志不构成合并证据。
- 触发：分支验收通过才允许进入受控集成；集成验收失败时保留失败证据，阻断后续 worker 集成，直到 leader 显式处理并对实际集成 HEAD 重验通过。恢复规则不能只删除失败标记。
- 执行器建议默认 argv 执行；超时处理本步骤及其子进程，记录 `timeout`。依赖失败的步骤记为跳过；无依赖步骤是否继续由契约明确声明。任何失败或超时导致整体非零退出，输出可定位的步骤和有界 stderr 摘要。
- 落点：新增 `scripts/verify.py`；控制器、schema、验证契约及派发模板。
- 本地验收：成功、失败、超时及子进程清理、自报与独立结果不一致；错误 SHA/旧任务/旧契约拒绝；A 验收失败后 B 集成被阻断；显式恢复并重验后可继续；磁盘恢复后阻断仍有效。
- 真实验收：T06 中真实双 worker 串行集成，证明测试针对实际分支与集成 SHA 执行，覆盖一次失败阻断。

### O02 · 最小报告 JSON 与身份校验

- [~] **O02**
- 现状：`accept_report()` 已检查身份相关字段，但没有 worker 文件报告的完整结构校验，也不会独立证明其自报的 Git 信息。
- 建议：worker 产出 `.threadweave/report.json`；保留 `threadId`、`branch`、`head`、`reportSha`、`taskRevision`、`baseIsAncestor` 现有字段，补充 run/role/attempt、`filesChanged[]`、`testsRun[]`、`selfReportedVerification[]`、`contractChanges[]`、`knownRisks[]`。若保留 `commitSha` 别名，必须与 head 一致。
- 先定义 `reportSha` 所指对象和哈希范围，避免 JSON 包含自身哈希的循环定义。报告内容与 leader 独立观察分别保存，worker 自报祖先关系不能替代 Git 核验。
- 触发：接收时校验结构、身份、任务修订、实际 branch tip、祖先关系及文件清单；O03 完成后增加范围核验。JSON 足以支持结构化接收或退回，但“接收”不等于“验收通过”。
- 保留 Markdown 作为解释性报告，机器门禁不依赖自由文本提取；testsRun 可引用 O01 步骤 ID，也允许标明额外自测。
- 落点：报告模板、`controller.accept_report`、schema、报告校验测试。
- 本地验收：缺字段报明确 JSON 路径；旧报告、错误身份、伪造文件清单被拒绝；保留原有身份门禁；自报通过不能生成 acceptance。
- 真实验收：真实 worker 生成侧车，leader 对照实际 Git 状态接收；证据归档后可回读。

### O03 · 写集预留与范围漂移两级检查

- [~] **O03**
- 现状：协议有范围要求，控制器没有统一的派发前写集检查与集成前路径检查。
- 建议：新增 `scripts/scope.py`，定义仓库相对路径、分隔符、大小写、`.`/`..`、符号链接及 glob 语义；拒绝越出仓库的声明。

### O11 · 失联识别与成果保全恢复

- [ ] **O11**
- 现状：recovery 已有 `reuse/revalidate/recreate/block/skip`；返回 recreate 不会删除旧成果，但缺少失联分类和明确的成果接续流程。
- 先定义策略再决定状态：unknown 表示尚不能确定；失联表示宿主证据异常但任务结果未定；failed 表示已确认失败。`lost` 是否加入 worker 状态表须说明与 blocked、failed、reuse/revalidate 的差别及合法迁移，不机械照搬子进程状态机。
- 触发与建议：
  - 查询超时、权限不足、列表暂不可见：未知，继续核验，不判定 thread 不存在。
  - thread 存在且 idle：核对未决派发、停止请求、任务修订、worktree 身份、branch/HEAD、base 祖先关系和已有报告，再由 leader 决定续接。
  - thread 确认不存在但 worktree 存在：先保全已提交及未提交成果，检查归属与冲突，再决定新 attempt 如何继承；缺失线程不是直接丢弃或重建的充分理由。
  - 脏 worktree：进入成果核验，不自动删除，也不直接发送恢复任务。
  - 线程仍 active 或派发结果未知：不续接、不替换，先核对与停止。
- resume 只有在证据充分且具备宿主要求的用户授权时执行；只读恢复建议不等于消息发送授权。recreate 保留旧 attempt 审计与资源记录，并遵守替换上限。
- 落点：recovery、控制器、状态表/schema（若决定新增状态）、leader 模板。
- 本地验收：查询失败不当作不存在；线程存在但旧停止证据/旧报告/未决派发时拒绝续接；脏成果保全；确认不存在后受控接续不丢旧审计；已有 reuse 路径不回归。
- 真实验收：T06 中验证一次中断恢复，保留恢复前后 branch、SHA、任务修订、线程状态及消息证据。不可用 fake adapter 声称宿主支持 resume。

## 第四批：最小环境准备与真实宿主验证

### O06 · 最小环境准备契约

- [ ] **O06**
- 现状：初始化预算默认 300 秒，没有独立 setup 契约；新 worktree 不包含所有本地环境文件。普通 status 不显示被忽略的文件，不能把环境缺失归因于门禁禁止补文件；现有 smoke 不能证明真实项目普遍的准备耗时或失败频率。
- O06a 最小范围：显式项目配置声明准备命令、cwd、超时、失败策略及幂等性；独立设置 `setupTimeoutSeconds`（建议默认 900）与初始化预算，明确阶段起止。未配置时保留现有行为。
- O06b 按需扩展：声明 `worktreeInclude` 的精确复制范围与目标，检查目标为 ignored/excluded 且位于本 worktree；敏感文件仅显式列出，不自动扫描复制 `.env*`，日志和归档不写入其内容。
- O06c 按需扩展：links/submodules 在真实需求出现后实现。共享可写 node_modules 等目录可能被安装或生成命令修改，必须有隔离或只读使用策略；不默认共享可写依赖目录。
- 触发：准备命令只来自已确认项目配置或用户指令，不能从 verify.json 自动推导授权；配置本身不是沙箱。准备失败阻断派发；成功后重新采集启动证据，保持原有身份、HEAD 与干净状态门禁。
- 准备超时与证据年龄分别配置；不能因为 setup 较长就延长旧证据有效期。准备修改 tracked 文件时门禁仍失败，需显式处理，不能静默放宽。
- 落点：配置契约、budget、控制器准备流程、启动/派发模板、schema。
- 本地验收：未声明命令拒绝；阶段分别计时；超时及失败阻断；准备后脏文件拒绝；旧启动证据不可复用；复制路径越界拒绝；不输出秘密内容；缺省行为兼容。
- 真实验收：结合 T06/L14 接入可用宿主，在一个具有真实依赖准备步骤的项目中跑双 worker，包含实际准备、独立验收及一次恢复/返工/失败路径。API 条件或授权不足时标记受阻，不编造结果。

## 后续维护与效率

### O13 · 分层 preflight 契约与失效

- [ ] **O13**
- 建议：O03/O06 字段稳定后，再引入 preflightId/contractHash；区分 run 级基线与宿主检查、worker 级 setup/ownedPaths 检查。规范化哈希不包含秘密明文。
- 触发：run 基线变化使相关全局证据失效；单 worker 范围或 setup 变化只失效其受影响检查。内容未变也需检查证据时效与实际环境变化，不能将哈希当作实时观测。
- 落点：控制器、startup_gate、preflight 模板与 schema。
- 验收：全局与局部失效分别覆盖；无关 worker 不被整体作废；旧格式兼容入口明确标记未验证，不冒充新契约验证成功。

### O14 · 绑定 SHA 的交付状态

- [ ] **O14**
- 建议：统一命名 `verified`、`landed`、`pushVerified`；分别关联验收 SHA、本地集成 SHA、远端与 ref 的实际观察 SHA 及时间。可使用分段记录，不以一个无 SHA 的字符串替代证据。
- 触发：独立验收通过产生 verified；实际合入并核验产生 landed；仅用户当次明确要求推送且远端核对通过才产生 pushVerified。默认交付停在本地 landed。
- 新提交产生后旧记录保留审计，但不得代表当前 HEAD；集成后仍需 O01 的集成验收，不把分支 verified 直接转成最终成功。
- 落点：控制器、schema、leader/最终报告模板。
- 验收：未推送不能出现当前成果的 pushVerified；错误远端/ref/SHA 拒绝；新提交使旧交付结论对当前成果失效；无自动 push 行为。

### O15 · compact 与增量读取

- [ ] **O15**
- 分两阶段：先 `status --compact`，再引入有明确定义与持久化来源的 `--since <cursor>`；当前 status 主要是 run 索引，应先确定摘要新增内容，不假定已有完整 overview。
- compact 字节预算可配置，7000 字节仅为候选初值；UTF-8 输出保持合法，优先保留身份、状态、下一步动作及省略标记。
- delta 需定义事件顺序、run 身份、重复读取、旧/非法游标与日志轮转的行为；不能用易变时间戳或状态 revision 假装完整事件历史。
- 原始 `report.json` 与 state.json 保持完整；超限报告拒收并说明路径，或另生成受限摘要，不能截断机器校验原件。
- 落点：CLI、run_log、报告摘要；仅有必要时扩展 schema。
- 验收：多字节输出受限且可解析；下一步动作不被无声省略；delta 无漏项且异常游标明确；所有读取不修改原始状态或报告。

### O16 · 三级清理计划与执行前重验

- [ ] **O16**
- O16a 计划阶段：保留当前 protect_* 原因，映射 SAFE/REVIEW/BLOCKED。SAFE 需已满足验收、干净、无未合并成果、报告归档、停止证据及资源归属；缺失/陈旧证据进入 REVIEW，不允许删除；脏资源、未合并成果、非本 run 或 primary/shared 资源进入 BLOCKED。
- 本地已验证并合入的资源可进入清理候选，不强制 pushVerified；保护完整成果才是条件。分支、归档报告和事件在本优化范围保留，不自动清理。
- O16b 执行阶段：待真实适配器与清理授权边界明确后，再为执行入口设计即时重验。重新采集路径、Git 注册、HEAD、脏状态、合并关系、归档和停止证据，对照计划 fingerprint；任何漂移都拒绝，不能把 fingerprint 当成持续安全保证。
- 落点：cleanup、CLI cleanup-plan；执行入口不属于 O16a。当前只有 dry-run，不宣称已存在 apply 前漏检导致的删除路径。
- 本地验收：三级分类保留具体原因；陈旧/缺失证据不给 SAFE；不推送仍可产生本地安全候选；plan 无删除副作用。O16b 另测计划后变脏、HEAD/归属变化及线程重新活跃时阻断。
- 真实验收：O16b 使用新鲜宿主/Git 观察验证归属与停止条件；不得删除活动 cwd 或绕过宿主所有权限制。
