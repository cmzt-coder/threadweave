## 第一批：机制补全（P0）

### O01 · 统一验证契约 `verify.json`

- [ ] **O01 统一验证契约**
- 现状：派发模板要求每个 worker 自带验证命令，命令散落在派发与报告中；leader 集成阶段需重新拼装。
- 建议：阶段 1 由 leader 写 `.threadweave/<run>/verify.json`，定义步骤、命令、工作目录、超时、期望退出码；worker 自查与 leader 合并且共用同一份。
- 落点：新增 `scripts/verify.py`；`references/worker-dispatch-template.md`、`references/preflight-checklist.md` 引用该文件路径。
- 验收：
  - `python3 scripts/verify.py --plan <path>` 顺序执行并汇总每步结果；
  - 任一步非零退出返回非零，并输出失败步骤名与 stderr 摘要；
  - 超时步骤被终止并标记 `timeout`，不阻塞后续步骤的汇总；
  - 新增 `tests/verify_smoke.py` 覆盖成功 / 失败 / 超时三例。
- 成本：约半天。依赖：无。

### O02 · 报告侧车 JSON 与机器校验

- [ ] **O02 报告侧车 JSON**
- 现状：`controller.accept_report` 要求 `threadId/branch/head/reportSha/taskRevision/baseIsAncestor` 六个字段，但这些字段由 leader 从自由文本中提取，无结构校验；leader 需通读 `report.md`。
- 建议：worker 同时产出 `.threadweave/report.json`，字段固定为 `commitSha`、`branch`、`filesChanged[]`、`testsRun[]`、`contractChanges[]`、`knownRisks[]`；leader 先读 JSON 判断是否接收，需要细节时再读 md。
- 落点：`references/worker-report-template.md` 增加 JSON 块；`controller.accept_report` 增加 `filesChanged`、`contractChanges`；`references/state.schema.json` 的 `workers[].report` 扩展。
- 验收：
  - 缺少 `filesChanged` 时 `accept_report` 抛 `ValueError`；
  - `report.json` 可独立校验，字段缺失/类型错误给出明确路径；
  - 仅凭 `report.json` 即可完成「接收 / 退回」判断（md 为可选阅读）。
- 成本：约半天。依赖：O01 的 `testsRun` 口径建议复用 `verify.json` 的步骤名。

### O03 · 范围漂移检测

- [ ] **O03 范围漂移检测**
- 现状：协议要求「everything asked, nothing extra」，但只能靠 leader 比对 diff；worker 顺手改无关文件时，发现时机在合并阶段。
- 建议：派发时声明 `ownedPaths`（glob 列表）与可选 `scopeExceptions`；集成前用 `git diff --name-only <base>..<head>` 对比，超出即标 `scope_drift`，要求 worker 说明并补授权，或回退。
- 落点：新增 `scripts/scope.py`；`controller.integrate` 在记录集成日志前调用；派发模板增加 `ownedPaths` 字段。
- 验收：
  - 文件集全部命中 `ownedPaths` → `ok`；
  - 存在未声明文件且不在 `scopeExceptions` → 返回 `scope_drift` 并列出文件；
  - glob 语义必须显式定义并有单测（建议用 `pathlib.PurePath.match`，并测试 `billing/*` 不匹配 `billing/sub/x.py`）；
  - 新增 `tests/scope_smoke.py`。
- 成本：约半天。依赖：无。

### O04 · `next` 命令：恢复时给出下一步动作

- [ ] **O04 `next` 恢复指令**
- 现状：`scripts/recovery.py` 已能算出 `skip/recreate/block/revalidate/reuse`，但没有命令入口；中断后需人读 `state.md` 与 `state.json` 自行推断。
- 建议：`python3 scripts/threadweave.py next --repo . --run <id>` 输出有序动作清单：需核对的 `dispatchIntent`、需重验的 worker、可复用观察的 worker、建议合并顺序、待清理资源。
- 落点：`scripts/threadweave.py` 增加 `next` 子命令，复用 `recovery.build_recovery_plan`、`state_store.latest_incomplete_run`、`cleanup.build_cleanup_plan`（只读）。
- 验收：
  - 给定 `dispatchIntent=unknown` 的状态 → 首条动作为 `revalidate`，并标注 role#attempt；
  - `complete` 且清理完成 → 输出「无需动作」；
  - `failed` 但清理未完成 → 输出待清理资源；
  - 命令只读：执行前后 `state.json` 的 mtime 与内容不变；
  - 新增 `tests/next_smoke.py`。
- 成本：约半天。依赖：无。**建议作为第一条实施项**（改动最小、立即改善恢复体验）。

## 第二批：真实场景护栏（P1）

### O05 · `rework` 次数上限

- [ ] **O05 返工上限**
- 现状：`controller.rework()` 只执行 `reworkCount += 1`，无上限检查；worker 连续改不对时会无限「返工 → 报告 → 返工」。
- 建议：`state.limits` 增加 `maxReworkPerWorker`（默认 2）；超限后必须二选一：走 `replace_worker` 替换，或 leader 接管修复并记 `leader_takeover`。
- 落点：`controller.rework`、`references/state.schema.json`（`limits` + `workers[].reworkCount`）、`references/leader-state-template.md`。
- 验收：
  - `maxReworkPerWorker=2` 时第 3 次 `rework` 抛错且状态不变；
  - 超限路径在状态中留下明确记录（替换或接管二选一，不允许静默继续）；
  - 现有 327 项断言不回归。
- 成本：约 2 小时。决策点：超限后的默认动作（替换 vs 接管），见文末。

### O06 · 环境准备阶段与初始化预算分档

- [ ] **O06 环境准备阶段**
- 现状：`budget.check_initialization` 默认 300 秒；真实 smoke 用时 107 秒是因为仓库零依赖。`npm install` / `poetry install` / `docker compose up` 常需 5–15 分钟，会被误判超时。
- 建议：
  - 新增可选 `setup` 阶段：启动核验通过后执行派发白名单内的准备命令；
  - 新增 `state.limits.setupTimeoutSeconds`（默认 900），与 `initializationTimeoutSeconds` 分开计时；
  - 明确准备阶段生成文件的处理规则（加入 `.gitignore`，或清理后再次声明 `status_porcelain` 为空）；
  - `startup_gate` 的 6 项检查不变，证据时效与 `setupTimeoutSeconds` 对齐。
- 落点：`scripts/budget.py`、`scripts/startup_gate.py`、`references/worker-startup-template.md`、`references/worker-dispatch-template.md`、`references/state.schema.json`。
- 验收：
  - 准备命令不在白名单 → 拒绝执行并给出原因；
  - `setup` 与 `validation` 分别记录耗时，超时判定互不影响；
  - `setup` 后工作区不干净 → 启动门禁失败并列出脏文件；
  - 未声明 `setup` 的 worker 行为与当前一致（向后兼容）。
- 成本：约 1 天。依赖：无。**这是「协议在真实项目上跑不起来」的头号原因。**

### O07 · 序列化资源单点归属

- [ ] **O07 序列化资源归属**
- 现状：`package-lock.json` / `poetry.lock`、迁移文件序号、路由表 / i18n 词条这类资源，多 worker 并行时几乎必冲突；当前协议没有识别机制。
- 建议：项目级配置 `.threadweave/config.json` 维护 `serializedPaths`；派发前扫描 `ownedPaths` 是否命中，命中即强制串行——只允许一个 worker 拥有，或要求全部 worker 不改、由 leader 集成后统一生成。
- 落点：新增 `.threadweave/config.json` 约定（git 排除目录内，或改为仓库根 `threadweave.config.json`，见决策点）；`scripts/scope.py` 增加检测；派发模板增加「串行资源」声明。
- 验收：
  - 两个 worker 的 `ownedPaths` 同时命中同一 `serializedPaths` → 派发前报错；
  - 单测覆盖 lockfile 与迁移序号两类；
  - 配置缺失时默认空列表，不改变现有行为。
- 成本：约半天。依赖：O03 的 path 匹配逻辑。

## 第三批：新协作逻辑（P2，按需）

### O08 · 契约冻结与契约改动检测

- [ ] **O08 契约冻结**
- 现状：「共享契约由 leader 提前定死」仅是文字要求，无机制保证 worker 不私改。
- 建议：leader 派发前把契约文件（OpenAPI 片段 / TS 类型 / migration 头）写入 `.threadweave/<run>/contracts/` 并记录 SHA；派发引用该 SHA；集成前校验各分支对契约文件的改动，违规标 `contract_violation`。
- 落点：`scripts/controller.py`（派发前记录、集成前校验）、`scripts/archival.py`（复用 SHA256）、`references/worker-dispatch-template.md`。
- 验收：
  - 契约 SHA 不匹配时集成前阻断；
  - worker 私改契约文件被识别并列出差异文件；
  - 未声明契约的 run 行为不变。
- 成本：1–2 天。前置：项目需存在稳定的契约文件，纯脚本类项目不适用。

### O09 · 制品交接（handoff）

- [ ] **O09 制品交接**
- 现状：A 生成中间产物给 B 使用时，若 A 尚未合并，只能通过 leader 转述或提前固定契约。
- 建议：`.threadweave/<run>/handoff/<name>` 存放不可变制品 + SHA；派发里携带 SHA；接收方开工前校验。
- 落点：`scripts/archival.py` 扩展或新增 `scripts/handoff.py`；派发模板增加 `handoff` 字段。
- 验收：
  - SHA 不匹配 → 启动门禁拒绝；
  - 已存在同名不同内容 → 抛冲突，不覆盖；
  - 无 handoff 的 run 行为不变。
- 成本：约 1 天。前置：任务确实存在多阶段依赖。

### O10 · 拆分预演（量化「该不该拆」）

- [ ] **O10 拆分预演**
- 现状：是否需要拆分完全依赖 leader 判断；`SKILL.md` 给了定性校准，但没有量化输入。
- 建议：基于 `git ls-files` 与各 worker 的 `ownedPaths`，计算文件重叠度、目录耦合度、序列化资源命中数，输出风险分与依据。
- 落点：新增 `scripts/split_preview.py`；`SKILL.md` 阶段 1 引用。
- 验收：
  - 输出必须包含计算依据（重叠文件列表、耦合目录、命中资源），不得只给分数；
  - 明确标注「仅供参考，不替代 leader 判断」；
  - 在积累 5–10 次真实 run 后再校准权重。
- 成本：2–3 天。前置：需要真实 run 数据校准，**建议最后做**。

## 暂不采纳（已评估）

| 方向 | 不采纳理由 |
| --- | --- |
| 多仓库 / 跨仓 monorepo run | 当前前提是「一个仓库根 = 一个 projectId = 一个集成 checkout」；跨仓需重写隔离与合并模型，成本远超收益 |
| 全自动合并（无 leader 审查） | 与「缺陷可归因」的核心价值直接冲突 |
| 可视化面板 | 当前瓶颈是协议能否在真实项目跑通，不是状态不可见；O04 的性价比高得多 |
| 通用调度层 / 多宿主抽象 | 会失去「Codex 原生线程」这一唯一差异化；与第三份文档路径 C 的结论一致 |
