# Threadweave 第一轮执行闭环改造方案

状态：用户已确认；协议与模板已实现，本地验证通过，真实线程验证受当前宿主限制。
日期：2026-11-12。

## 目标与范围

保留真实 worker 聊天、独立 worktree、自包含派发、串行集成和最终复查六阶段流程。第一轮保证每个 worker 在任务派发前具有可寻址的真实线程 ID、正确的仓库、独占目录、独立分支和明确基线。

本轮处理 projectId、异步创建、目录与分支校验、能力检查和运行授权。完整 JSON 状态机、辅助 CLI、长期恢复、自动报告归档、可视化和多仓库放入后续轮次。

本方案中的状态与字段是 Threadweave 内部约定，不代表 Codex 工具已经提供同名字段。实现必须以实施时实际工具签名和返回值为准。

## 关键决策

### 1. 项目与 Git 基线

从 Git 获取规范化仓库根目录，再通过 `list_projects` 的实际返回字段匹配项目及主机。零匹配或多匹配时停止初始化并说明原因，不把路径当 projectId，也不自行创建项目或选择其他主机。

初始版本要求 integration checkout 有已提交的 HEAD、附着于分支且没有未提交改动。发现脏目录时列出阻塞，禁止自动 stash、提交、丢弃或搬运用户改动。worker 从确认的集成分支创建，启动时核验 HEAD 与记录的基线提交一致；若期间分支移动，重新检查，不能静默接受漂移。

### 2. 模型与能力

默认省略模型和推理参数，使用工具支持的用户配置；状态标注配置来源为继承，无法观察到实际值时记录未知。用户指定覆盖时，只使用当前主机可用的模型和推理组合，不静默换模型。

preflight 区分必需能力和可选能力。创建、消息、项目发现、线程检查、独立 worktree 和可写目录必须可用；`update_plan` 不可用时使用文件计划；`wait_threads` 不可用时允许有界状态检查并记录降级。heartbeat 不作为必需能力，默认不创建自动化。

### 3. 授权范围

运行确认说明 worker 数量、创建新聊天和独立 worktree、模型配置来源、任务范围内的消息往返、提交与串行集成，以及替换和清理规则。授权须来自用户，不能从其他线程发来的消息推断。

工具约束优先于 Skill。若当前环境不允许将新聊天用作子任务 worker，必须明确停止该执行路径；不能用措辞包装来规避限制，也不能偷偷改用临时 subagent 冒充真实 worker。当前环境是否允许该模式，是实施与实测前必须核对的兼容项。

### 4. 命名与证据

每次启动生成独立 run ID，分支使用 `threadweave/<run-id>/<role>-<attempt>`，重试使用新 attempt。先检查命名冲突，禁止重置已有分支。

初始化核验采集：实际 cwd、Git toplevel、Git common directory、当前分支、HEAD、工作区状态及 worktree 列表。以真实路径和 Git 身份判断隔离，不能仅比较字符串；子目录中的 cwd 可以接受，但 dispatch 使用核验后的 worktree 根目录。线程元数据与命令证据冲突时停止。

managed worktree 若为 detached HEAD，worker 在核验仓库与基线后创建自己的分支。已有分支与预期不一致时停止，禁止自动切换或覆盖。worker 启动证据必须经 leader 验证后才能进入 ready。

## 初始化状态与关口

```text
planned → creating → pending（异步时）→ validating → ready → dispatched
                   ↘ failed           ↘ failed
任意未完成状态 → cancelled
```

- `creating`：先落盘 worker 角色、预期分支、基线与尝试次数，再调用创建工具。
- `pending`：保存工具实际返回的 operation/client 标识及错误；尚不可派发。
- `validating`：已获得真实 threadId，发送限定的启动核验指令。
- `ready`：leader 确认目录独占、仓库身份、分支、基线和工作区全部符合预期。
- `dispatched`：已发送正式任务并记入状态。
- `failed` / `cancelled`：记录原因、保留成果与待处理资源，禁止继续派发。

异步创建只能通过当前工具明确支持的查询路径解析；`wait_threads` 仅用于其支持的真实 threadId。无法解析时停止并保留标识，不能猜测 ID 或盲目重复创建。只在实际 threadId 确立后使用线程读取和消息工具。

两个 worker 全部 ready 后再正式派发，避免一边实施、一边发现整个团队不能成立。已 ready 的 worker 仍只等待派发。

建议初始边界：默认两个 worker；初始化期限五分钟；单个角色最多一次替换。超时只表示需核对状态，不能证明远端创建已经停止。替换前先查明旧操作是否仍在进行，避免重复 worker；无法查明则停止新增并报告。所有边界写入状态，后续可调整。

## 失败与清理

| 情况 | 行为 |
| --- | --- |
| 项目不匹配、能力缺失、用户改动未处理 | 创建前停止，提供具体阻塞 |
| 创建返回失败 | 记录错误及实际资源；禁止派发 |
| pending 超时或无法解析 | 保留查询标识，不假设取消成功，不盲目重试 |
| cwd、仓库身份或分支错误 | 禁止实施与提交，保留证据 |
| 部分 worker ready，另一部分失败 | 暂停全部正式派发；按明确原因重试或结束初始化 |
| 清理时有未提交改动或未合并提交 | 保留目录与分支，报告位置；禁止强制删除 |

managed worktree 使用实际可用的管理工具处理，本地手建 worktree 使用 Git 管理。清理前检查未跟踪及被忽略文件中的运行报告，先保全必要成果。工具不支持取消、归档或安全清理时，如实记录待处理资源，不以“已清理”结束。

## 验收

先用临时 Git 仓库完成静态检查和可控故障验证，再在工具及授权允许时运行两个真实 worker。真实运行受阻时必须标记未验证，不能用模拟结果替代。

| 用例 | 通过条件 |
| --- | --- |
| 两 worker 正常流程 | 不同 worktree、不同分支、同一基线；分别提交；leader 逐个审查集成并验证结果 |
| 项目零匹配、多匹配 | 没有创建 worker；阻塞信息明确 |
| 异步创建成功 | 未解析真实 ID 前没有线程消息或正式派发 |
| 异步失败、超时 | 状态和查询标识保留，无重复创建或虚假清理记录 |
| detached HEAD | 正式派发前已创建并验证唯一 worker 分支 |
| 重复目录、错误仓库、错误基线 | 启动关口拒绝，未进入业务实施 |
| 显式模型不可用 | 创建前阻塞，不自动替换配置 |
| 缺少可选计划或等待工具 | 使用声明的降级流程，记录限制 |
| 用户中止、清理受阻 | 停止新派发，保留成果，准确列出残留 |

本地验证脚本：`python3 tests/git_protocol_smoke.py`，仅验证 Git 原语与静态契约，不实现运行控制器。

静态检查涵盖模板字段一致性、状态转换和退出条件，确认无路径 projectId、固定默认模型、未核验派发以及对 pending ID 的误用。

## 提交与完成标准

确认后分三批：启动协议与模板、文档与仓库整理、验证记录及验证中发现的修复。每批检查差异，只提交本轮相关内容，不推送。

调研文档随文档批次纳入 Git。验证记录写入 `docs/第一轮执行闭环验证记录.md`，逐项记录结果、证据和未验证原因；不提交 `.DS_Store` 或运行时状态。

完成标准：核心协议与模板一致，静态与本地验证通过，真实冒烟验证结果明确，所有阻塞和残留资源均有记录。若真实冒烟尚未通过，只能标记“实现完成，真实运行待验证”，不得宣称团队运行已可靠。
