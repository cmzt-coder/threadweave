# O16 资源来源映射与宿主字段适配记录

日期：2026-11-16。范围：创建账本与宿主原始资源回执的只读来源映射，以及已观察附件字段的兼容修正。状态：本地实现和受控集成验证通过；当前真实宿主的可信所有权/保护状态观察仍缺失，O16 未关闭。

## 发现的问题

此前清理门禁按附件的 `type` 字段查找 worktree。历史真实原始回执已经证明，当前宿主附件实际使用 `attachmentType`：

```json
{
  "attachmentType": "worktree",
  "identityKey": "/absolute/worktree",
  "payload": {
    "hostId": "local",
    "root": "/absolute/worktree",
    "workspaceRoot": "/absolute/worktree",
    "sourceCwd": "/absolute/repository"
  }
}
```

归档附件使用 `attachmentType=archived_worktree`，资源身份位于 `payload.worktree`。上述实际结构没有暴露 `ownerThreadId`、`runId`、`isPrimary`、`isShared` 或调用者聊天身份。

因此本轮同时做两件事：

1. 接受真实 `attachmentType` 及历史 fixture 的 `type`，但字段冲突时拒绝，绝不从附件推测所有权或清理权限。
2. 新增独立、只读的来源映射器，用项目创建账本把外部资源关联到精确的 runId/role/attempt/taskRevision；映射结果始终 `cleanupEligible=false`。

## 功能节点与精确触发条件

### 附件字段规范化

- `attachmentType` 优先，兼容旧 `type`；两个字段同时存在但不一致时返回 `conflicting artifact type fields`。
- 缺失或空类型、附件不是对象时拒绝。
- 输出深拷贝并增加规范化字段 `kind`，不修改原始输入，不补写 `ownerThreadId`、`isPrimary`、`isShared` 或 `runId`。
- `archived_worktree` 只能说明归档附件存在，不能作为当前活动附件或删除成功证据。

### 来源关联成功

以下条件必须全部满足，才会返回 `associated` 或 `associated_archived`：

- 创建和附件观察都是成功账本操作，method 分别为 `create_worktree`、`list_artifacts`。
- 账本绑定的 `runId`、`role`、`attempt`、当前 `taskRevision` 精确匹配清单；创建回执绑定精确的 `createdTaskRevision`。
- 原始回执文件是绝对、非符号链接的 JSON；文件 SHA256 等于账本 `toolResultSha`，解析内容等于账本持久化 `metadata.result`。
- 创建请求的 `sourceRoot` 精确等于规范化后的本地仓库根目录。
- 创建回执仅接受已实证的同步格式：`type=created`、`registrationError=null`，且两个 worktree root 都精确等于目标路径。异步、未决或未知格式不会猜测完成。
- 清单观察时间距当前为 0–30 秒，且不早于创建观察时间。
- 附件 `identityKey` 唯一且精确等于目标 worktree；active payload 或 archived `payload.worktree` 的 `hostId/root/workspaceRoot` 必须精确匹配 `local` 和目标路径。
- 允许任务版本从创建版本向前推进，但 `createdTaskRevision > taskRevision` 一律拒绝。

### 必须阻断

- runId、role、attempt、taskRevision、创建版本或 operation 不匹配。
- 账本操作未成功、请求绑定漂移、原始文件哈希漂移、账本 metadata 与原始内容不一致。
- 原始文件路径不是绝对路径、本身是符号链接或无法读取。
- 创建为 pending/queued/未知格式，清单早于创建，或清单过期/时间在未来。
- 资源路径不是规范化绝对路径、来源仓库不匹配、资源身份缺失或重复。
- payload host/root/workspaceRoot 不匹配、字段类型冲突、附件清单为空。
- 任何情况下，仅凭本地账本和路径关联都不足以授权停止、归档或删除。

## 接口

新增 `scripts/resource_provenance.py`，提供：

- `normalize_artifacts(result)`：只读规范化附件列表。
- `parse_raw_result(raw)`：只接受成功 MCP envelope 中唯一 JSON 文本结果。
- `map_resource_provenance(spec, now=None)`：验证账本、原始回执、版本、时效和资源身份。

CLI：

```sh
python3 scripts/resource_provenance.py /absolute/path/manifest.json
```

清单示例：

```json
{
  "repository": "/canonical/repo",
  "worktree": "/canonical/worker",
  "runId": "run",
  "role": "a",
  "attempt": 1,
  "createdTaskRevision": 0,
  "taskRevision": 2,
  "createOperation": "create",
  "createRaw": "/absolute/create-raw.json",
  "inventoryOperation": "inventory",
  "inventoryRaw": "/absolute/inventory-raw.json"
}
```

关联成功时 CLI 退出码为 0，blocked 时为 1。退出码 0 只表示来源关联成功，不表示可清理。

## 输出与安全边界

成功结果固定包含：

- `readOnly=true`
- `deletionPerformed=false`
- `cleanupEligible=false`
- `runAssociationVerified=true`
- `unknown=["ownerThreadId","isPrimary","isShared","callingThreadId"]`

当前映射不证明：

- Git HEAD、分支、工作区 clean、成果已合入或报告完整。
- worker 已停止、turn 已结束或聊天已归档。
- 资源所有者、primary/shared 状态、调用者作用域或宿主保护状态。
- 宿主签名或对恶意本地写入者的防护；本地 SHA256 只能防止误关联和普通漂移。

`managed_cleanup.py` 本轮只修正了附件类型识别，仍保留原停止证据、所有权、primary/shared、Git 安全、计划 fingerprint 和明确批准门禁。来源映射器尚未替代这些放行条件，也没有被接入删除流程。

## 未关闭项与下一步

O16 仍需建立以下证据闭环，之后才能考虑把来源映射纳入清理门禁：

1. 可信所有者与调用者作用域：证明目标资源属于指定 worker，且当前调用范围可授权操作。
2. primary/shared/保护状态：获得可验证观察，或采用宿主执行时保护且结果可复核的独立方案。
3. 新鲜停止证据与精确 Git 计划复核仍必须同时成立。
4. 真实正向归档和最终资源消失/归档回执必须新鲜采集，不能复用历史回放。

下一步应优先评审“调用者作用域 + 保护状态”的证据设计，不把只读关联成功当成删除授权，也不通过反复创建真实聊天或降低现有门禁来碰运气。异步创建适配、未知回执格式和宿主签名能力需要单独设计。
