## P1：执行安全约束（建议优先）

- [x] **L01 正式派发可以绕过完整启动门禁**
  - 问题：目标 worker 为 ready 且有非空 threadId 时，省略 startup_report 仍会发送；另一 worker pending、run initializing 也能派发。
  - 建议：把门禁证据绑定到 run / role / attempt / 仓库身份 / 基线 / 观察时间；派发前校验 run 阶段、团队门禁、目标身份与集成 HEAD。
  - 验收：缺证据、他人证据、过期或不匹配证据、另一 worker 未初始化、集成漂移均零消息；A 派发后仍可正常派发 B。

  - 进展（2026-11-12）：`Controller.dispatch` 强制 `startup_report`/`expected`，校验团队门禁与集成 HEAD；缺证据、团队未 ready、集成漂移均零消息。剩余：证据持久化、他人/过期证据、A→B 顺序测试。
  - 进展（2026-11-12）：`dispatch` 强制启动证据、团队门禁、集成 HEAD；证据绑定 role/attempt 并持久化；他人证据、过期证据、A→B 顺序均已测试。
- [x] **L02 消息发送与状态保存之间存在重复执行窗口**
  - 问题：adapter 已发送消息、随后持久化失败或进程退出时，磁盘仍为 ready，重启后可能重复发送。
  - 建议：外部调用前持久化唯一 dispatch ID、任务摘要与发送意图；区分 sent / unknown / acknowledged，不确定时先核对 worker，不自动重发。
  - 验收：发送前、发送中、发送后保存分别注入失败；恢复后不得盲目重发，也不能把 unknown 宣称成功或失败。
  - 进展：发送前持久化 intent；发送前/后保存失败均注入测试；pending/unknown 恢复返回 `revalidate`，不盲目重发。
- [x] **L03 恢复把未知误判为不存在，并对完成后的 HEAD 使用启动规则**
  - 问题：pending 有 clientThreadId、无 threadId、观察为空时返回 recreate；reported worker 正常提交后 HEAD 不等于 baseSha 时返回 block。
  - 建议：外部观察使用 exists / missing / unknown 三态；pending 先解析，unknown 先重验；初始化阶段检查 HEAD == base，执行后检查 base 祖先关系、报告 SHA 与 branch tip。
  - 验收：pending 未决、查询失败、真实不存在、正常完成提交、范围不符提交分别得到不同动作。
  - 进展：恢复支持 `thread_exists` 三态、pending 先解析、reported 使用 base 祖先关系与报告 SHA；`recovery_smoke.py` 17 项通过。
- [x] **L04 清理动作没有受停止证据和资源归属共同约束**
  - 问题：缺少完整停止证据时仍可能返回 remove；缺失 Git 观察被当作干净；primary 或非本 run 资源未约束。
  - 建议：删除门禁统一检查观察结果、归属、primary/shared、停止证据、Git 状态、未合并成果、忽略文件保全与报告哈希；任何未知返回保护原因。
  - 验收：缺任一必需证据不能返回 remove/delete；只有完整确认的专用资源才可给出清理动作。
  - 进展：清理门禁检查 `owned_by_run`、`is_primary`、未知 Git 观察与完整停止证据；`cleanup_smoke.py` 20 项通过。
- [x] **L05 结构化状态契约与控制器实际输出不一致**
  - 问题：控制器写入 `dispatchAt`、`plan`、`lastCreateError` 等字段不被 `state.schema.json` 接受；save 未校验。
  - 建议：区分通用原子 JSON 写入与受校验的 run-state 存储；强制版本、类型与领域不变量；统一计划、错误、派发、启动证据、模型配置与授权字段。
  - 验收：使用完整 schema fixture 运行控制器；所有输出均合法，非法状态与跨字段冲突在任何宿主副作用之前拒绝。
  - 进展：schema 扩展控制器实际字段；`validate_state` 强制 schema + 跨字段不变量（worker 身份唯一、complete 要求 finalReview/cleanup 完成）。
- [x] **L06 原子写入和文件锁尚未组合成受保护的状态更新**
  - 问题：两个控制器持有同一 run 的旧快照时，后保存者会覆盖前者，导致业务更新丢失；StateLock 未被控制器使用。
  - 建议：持有 run 排他锁执行「读最新状态 → 校验 revision → 更新 → 持久化」；拒绝旧 revision；外部调用另用持久化意图协调。
  - 验收：多进程同 run 竞争、过期快照、异常释放、进程退出后恢复均有明确结果；不同 run 仍独立。
  - 进展：`StateLock` + revision 拒绝旧快照；异常释放、跨进程互斥、进程退出自动释放均已测试。

## P2：完整生命周期与适配

- [x] **L07 返工、停止请求与失败后的清理不是完整生命周期**
  - 问题：`reported → running` 被拒绝，无正式返工入口；aborted 且 cleanup pending 时 `latest_incomplete_run` 返回 None；replace_worker 未核对停止证据或已有后续 attempt。
  - 建议：分别管理执行结果与资源清理结果；恢复扫描包含失败/中止后的清理债务；引入显式返工任务修订与停止请求/确认流程；替换预算从持久状态读取。
  - 验收：报告退回后能正常返工；取消请求成功但线程仍 active 时禁止替换和删除；aborted 后未清理资源仍能被定位。

  - 进展（2026-11-12）：增加返工（reported→running）、停止请求/确认；替换前要求停止证据、无后续 attempt，并从持久状态读取替换上限；failed/aborted 的清理债务仍可定位。
- [x] **L08 归档未按 attempt 与返工修订隔离**
  - 问题：同 role 先归档 attempt 1 的 report.md，再归档内容不同的 attempt 2 同名报告会抛 ArchiveConflict；manifest 更新未加锁。
  - 建议：使用 `reports/<role>/<attempt>/<revision>/` 与包含身份的 manifest 键；临时文件复制完成后校验目标，再原子发布；manifest 更新在锁内执行。
  - 验收：不同 attempt/修订并存；同身份同内容幂等；同身份不同内容拒绝；并发、中途失败、来源变化不会产生可误信的完整归档。

  - 进展：归档改为 `reports/<role>/<attempt>/<revision>/`，manifest 键包含 attempt/revision；不同 attempt 同名报告并存测试通过。
- [x] **L09 run 与归档目标缺少路径边界验证**
  - 问题：`run_state_path(root, '../escape')` 可写出 `.threadweave`；归档 role 为 `../outside` 可写出 reports 目录。
  - 建议：验证 runId / role / 文件名为允许的单段标识；拒绝绝对路径和父目录段；对规范化目标与符号链接做包含关系检查。
  - 验收：路径穿越、绝对路径、符号链接跳出均在写入之前拒绝；合法标识行为不变。
  - 进展：runId/role/artifact name 拒绝路径穿越、绝对路径与符号链接；合法标识行为不变。
- [x] **L10 预算和停滞判断没有区分阶段与有效进展**
  - 问题：archived worker 仍被标为 initialization deadline_exceeded 与 stalled；`lastObservation` 混合「leader 看过」和「worker 有进展」；宽限按最后活动时间推导。
  - 建议：区分 lastCheckedAt / lastProgressAt / statusRequestedAt / graceDeadline；只对适用阶段计算期限；先请求状态再给完整宽限。
  - 验收：终端态不报停滞；反复查询不刷新进展时间；请求未成功发送不能开始宽限；新进展取消旧停滞判定。

  - 进展：`check_stall` 区分进展/状态请求/宽限；终态返回 not_applicable；先请求状态再给完整宽限；新进展取消旧停滞判定。
- [x] **L11 宿主适配接口尚不足以兑现创建超时与降级执行**
  - 问题：`resolve_project` 接受缺少 projectId 或 hostId 不匹配的记录；`create_worker` 的 timeout 未传入适配器；wait 降级只返回模式描述。
  - 建议：增加带 host 的项目解析与 ID 校验；定义结构化创建/错误结果、pending resolver、能力快照、等待 cursor 与可选停止能力；分层「生成计划」与「执行宿主调用」。
  - 验收：本地测试分别说明异常处理、超时调度、降级计划与真实降级；接入真实适配器后再补真实线程验证。

  - 进展：`resolve_project` 增加 host/projectId 校验；`HostAdapter.capability_snapshot`；`Controller.record_capabilities` 持久化能力快照；`create_worker` 在 `create_timeout` 能力下传递 timeout。真实宿主适配器待接入。
- [x] **L12 文档、恢复入口和测试对外契约需要统一**
  - 问题：Skill 以 state.md 为权威记录，Python 扫描与教程使用 state.json；state.json 为数组时 locate_runs 抛异常；CLI preflight 失败仍返回 0；文档仍有早期描述与已过时发布状态。
  - 建议：选定唯一机器状态源，Markdown 作为派生视图；新增 inspect / recover-plan / doctor 等只读诊断入口；明确 CLI 失败退出码与输入错误格式。
  - 验收：仅 Skill 运行与辅助模块运行均有明确恢复方式；损坏/错类型状态可诊断；自动化可通过退出码识别 preflight 失败。

## 推荐推进顺序

1. **第一批（执行安全）**：L01–L06，先纳入 L09 的输入边界检查；为取消和替换加入保守的停止证据检查。
2. **第二批（完整生命周期）**：L07、L08、L10、L12；先形成可审查的动作计划，再接执行。
3. **第三批（宿主适配）**：L11，并建立兼容维护流程。
4. 每批完成标准：本地故障用例通过、原有正向流程保持可执行、未验证的宿主能力继续如实标记。
