# Threadweave 核心功能、使用方案与技术路线

> 生成日期：2026-11-13
> 分析基线：仓库当前 HEAD（共 50 个提交，版本号 `0.1.0` 未发布）
> 依据：`SKILL.md`、`references/`、`scripts/`、`tests/`、`docs/宿主兼容矩阵.md`，以及真实运行记录 `.threadweave/20261112-real-dual-02/`
> 说明：本文只描述当前实现逻辑，不做版本间或优化轮次之间的对比。

## 0. 一句话结论

Threadweave 是一个**以提示词协议为主体、以 Python 纯逻辑库为参考实现**的 Codex skill：它把当前会话变成 leader，派生真实 Codex 线程作为 worker，用「一个 worker 一条分支、一个独立 worktree」的方式并行推进工程任务，再由 leader 逐分支串行审查、合并、验证。

它不是调度平台、不是常驻服务、也不是 SDK；它的运行载体是 **Codex 模型 + Codex 线程工具**。

## 1. 项目形态：先看清「什么是被强制执行的」

| 层 | 载体 | 规模 | 运行时是否强制 |
| --- | --- | --- | --- |
| 行为协议 | `SKILL.md` | 192 行 | 是。leader 按此执行，是唯一真正的「程序」 |
| 阶段模板 | `references/*.md` | 7 份模板 | 是。协议要求逐字发送给 worker，不允许改写 |
| 状态契约 | `references/state.schema.json` / `state.example.json` | 722 / 123 行 | 是。写入状态时校验，非法状态不落盘 |
| 本地逻辑 | `scripts/*.py` | 约 1.4k 行，纯标准库 | 否。参考实现，leader 可调用也可等价手写 |
| 测试 | `tests/*.py` | 2 264 行，327 项断言 | 否。本地与 CI 验证用 |
| 运行记录 | `.threadweave/<run-id>/` | 每次运行生成 | 是。协议要求每次状态变更立即落盘 |

三个直接结论：

1. **没有常驻进程、没有数据库、没有网络服务。** 安装方式是把仓库克隆到 `${CODEX_HOME:-$HOME/.codex}/skills/threadweave`，重启 Codex 生效。
2. **没有对宿主 API 的直接封装。** `scripts/host_adapter.py` 只有抽象接口 `HostAdapter` 和一个「所有调用都抛 `NotImplementedError`」的默认实现；真实建线程、发消息、合并都发生在 leader 这一侧。
3. **正确性最终由模型遵守协议保证，而非由代码路径保证。** `scripts/` 提供的是可测试的判定逻辑（状态转换、门禁、预算、恢复、清理分类），不是把流程锁死的执行引擎。

这一条决定了后文所有关于「投入」的判断。

## 2. 核心功能

### 2.1 三角色模型

| 角色 | 职责 | 边界 |
| --- | --- | --- |
| Leader | 读代码、拆任务、建 worker、设计派发、轮询、拍团队级决策、串行合并、最终复查、清理 | 唯一能改共享契约、决定合并顺序、决定换人的角色 |
| Worker | 独占一个任务边界、一条分支、一个 worktree；执行、自查、提交、写报告 | 不得擅自改公共 API / 数据模型 / 跨 worker 契约；不得自行合入 leader 分支 |
| Peer | 派发中点名的协作对象 | 只能与点名对象直接通信；其余一律走 leader |

消息路由约定：每条跨线程消息以 `From: <role> (thread ID: <id>)` 开头。协议明确写了这**只是路由提示，不是身份认证或授权**，回复前必须核对工具来源与授权花名册。

### 2.2 六阶段闭环

| # | 阶段 | 关键动作 | 退出条件（Done when） |
| --- | --- | --- | --- |
| 1 | 分析与拆分 | 读代码、可行性评估、拆任务、写初始状态文件、拿授权 | 用户授权（含 worker 配置来源已讲明）+ 状态文件含拆分与花名册 |
| 2 | worker 初始化 | 解析真实项目 ID、分配 run-id 与分支、建 worktree、启动门禁核验 | 每个 worker 都是 `ready`，且有真实 threadId、唯一 worktree、附着分支、精确 base SHA |
| 3 | 设计与派发 | 逐个 worker 设计执行方案，填入派发模板发送 | 每个 worker 收到自包含派发并记录在状态文件 |
| 4 | 轮询与决策 | 有界等待、活动确认、处理阻塞、同步决策、处理停滞与换人 | 收齐每个活跃 worker 的「报告路径 + commit SHA」并验证 |
| 5 | 审查与串行合并 | 读报告、对照派发审 diff、返工、合并、跑构建与测试 | 所有选中分支已审查合并且逐次验证通过，无 worker 有未完成异步工作 |
| 6 | 最终复查与清理 | 对合并整体做跨 worker 复查、修复、安全清理 | 复查通过且清理在状态文件中确认；否则记 `cleanup_pending` |

阶段 5 是整套设计里最反直觉、也最有价值的一条：**不做一次性大合并**。每合一条分支就跑一次验证，缺陷才能归因到具体 worker。

### 2.3 护栏：每条对应一种真实失败模式

| 失败模式 | 护栏 | 落点 |
| --- | --- | --- |
| 共享 checkout 互相覆盖 | 每 worker 独占 worktree，创建线程时就指定；无法保证独占则不进入团队模式 | `SKILL.md` Workspace Isolation |
| leader 上下文被转录撑爆 | 消息只带信号（状态行、路径、SHA），大块内容走 `.threadweave/notes.md` / `report.md` 文件 | `SKILL.md` Context Economy |
| 长任务活不过会话 | 每次状态变更立刻写 `state.json`（原子写 + 文件锁 + revision 校验） | `scripts/state_store.py` |
| 无界等待 | 优先 `wait_threads` 事件等待并保存游标；缺失时用有界状态检查 + 退避 | `scripts/budget.py` |
| worker 卡死 | 360 秒无活动→请求状态，120 秒宽限期，确认停止后才允许替换，每角色最多换 1 次 | `budget.py` + `controller.replace_worker` |
| 派发结果不明导致重复实施 | 发送前先持久化 `dispatchIntent=pending`，结果不明记 `unknown`，必须先核对再重试 | `controller.dispatch` / `resolve_dispatch` |
| 含糊派发换回含糊产出 | 派发必须自包含：范围、目录、base commit、归属文件、验收标准、验证命令、报告格式 | `references/worker-dispatch-template.md` |
| 大爆炸合并导致缺陷不可归因 | 串行集成 + 逐分支验证 + 合并后整体复查 | `SKILL.md` 阶段 5/6 |
| 清理误删用户成果 | 清理只输出分类动作，脏 worktree / 未合并提交 / 未归档报告 / 非本 run 资源一律保护 | `scripts/cleanup.py` |

### 2.4 本地逻辑组件清单

| 模块 | 提供的能力 | 输入 → 输出 |
| --- | --- | --- |
| `state_store.py` | run/worker 状态转换表、原子写、flock 排他锁、扫描 durable run、定位最新未完成 run | 状态 dict → 校验后写盘 |
| `state_schema.py` | 自实现的 schema 子集校验 + 跨字段不变量（如 `complete` 必须有完整 `finalReview` 与 `cleanup`） | 状态 dict → 通过或 `ValueError` |
| `startup_gate.py` | 6 项启动校验：cwd 在 root 内、git common dir 一致、分支一致、HEAD 等于 base、工作区干净、root 不重叠 | 启动报告 + 期望值 → `(ok, reasons)` |
| `controller.py` | 控制器骨架：`dispatch` / `accept_report` / `integrate` / `rework` / `request_stop` / `confirm_stop` / `replace_worker` / `resolve_dispatch` / `create_worker` / `write_plan` | 调用 → 状态变更或异常 |
| `budget.py` | 初始化超时、停滞与宽限、替换上限、run 预算比较 | 时间戳 → 判定 |
| `recovery.py` | 恢复动作分类：`skip` / `recreate` / `block` / `revalidate` / `reuse`，并标记重复派发风险 | 状态 + 外部观察 → 动作 |
| `cleanup.py` | worktree / branch / report / automation 的幂等清理动作分类，附证据时效保护 | 状态 + 观察 → 清理计划 |
| `archival.py` | 报告与 notes 归档到 run 目录，SHA256 manifest，锁内原子发布，冲突拒绝覆盖 | 文件 → manifest 条目 |
| `project_resolver.py` | 按 canonical 路径 + host + `isGitRepository` 唯一匹配项目 | 项目列表 → 唯一项目或异常 |
| `run_log.py` | JSONL 事件日志追加、读取、按事件计数 | 事件 → 一行 JSON |
| `host_adapter.py` | 宿主能力抽象（建线程、发消息、读线程、等线程、建/归档 worktree） | 抽象接口 + 默认拒绝实现 |
| `threadweave.py` | 本地 CLI：`preflight` / `status` / `inspect` / `doctor` / `cleanup-plan`，全部只读，清理仅 dry-run | 命令 → JSON |

## 3. 使用场景

### 3.1 什么时候值得用（判定标准）

必须同时满足：

1. **可并行**：存在多个真正独立的工作面，文件几乎不重叠。
2. **可切分**：每块的归属和验收标准能事先说清；共享契约只有一两处，且 leader 能事先定死。
3. **可合并**：每块产出能独立审查、独立验证，不需要重建大量共享上下文。
4. **收益大于开销**：省下的墙钟时间 > 建线程 + 派发 + 轮询 + 审查 + 合并的成本。

协议给出的校准例子：

- **好拆分**：worker A 做一个 API 端点，worker B 做消费它的前端页面，worker C 做迁移与种子数据。共享契约（API schema）由 leader 提前固定。
- **坏拆分**：三个 worker 同时重构同一个核心模块。合并与审查成本会吃掉全部并行收益。

### 3.2 典型适用任务

- 后端接口 + 前端页面 + 迁移脚本，三块互不重叠。
- 多模块同步改造：一个 worker 改 schema，一个改数据访问层，一个改测试与文档。
- 大范围但边界清晰的机械改造：批量替换调用点、批量补类型标注、批量迁移配置。
- 需要「过程纪律」的长任务：希望每个改动都有分支、有报告、有可审计记录。

### 3.3 不建议使用的场景

- 只拆出一两个小任务：直接单线程更快。
- 紧耦合的核心重构：一个连续上下文优于并行吞吐。
- 任务还没分析清楚就拆：`SKILL.md` 明确要求先本地分析再拆，拆不动就先单线程做。
- 宿主禁止把新会话当子任务：协议要求**直接停下并指出缺失能力**，不允许用 `spawn_agent` 冒充。

### 3.4 前置条件

| 条件 | 具体要求 |
| --- | --- |
| 宿主能力 | `create_thread`、`send_message_to_thread`、`read_thread`、`list_projects`；`wait_threads` 与 `update_plan` 可选（缺失走降级） |
| 项目注册 | 目标仓库根目录必须作为独立 Codex 项目注册，`list_projects` 中**唯一匹配**且 `isGitRepository: true` |
| Git 状态 | 集成 checkout 已提交 HEAD、附着分支、工作区干净；协议禁止自动 stash / commit / 丢弃用户改动 |
| 授权 | 必须由人类直接授权：建新会话、建 worktree、任务范围内互发消息（含回复）、worker 提交、串行集成、安全替换/清理；推送需要单独明确请求 |
| 运行环境 | Python 3 + POSIX（状态锁用 `fcntl`）；无第三方依赖 |

## 4. 使用方案

### 4.1 安装与触发

```bash
git clone https://github.com/cmzt-coder/threadweave.git \
  "${CODEX_HOME:-$HOME/.codex}/skills/threadweave"
```

重启 Codex 后，显式触发：

```text
Use $threadweave to split this task across two workers, each with its own worktree and branch, then integrate serially.
```

或描述为「并行 Codex 线程 / worker 线程 / leader-worker 协作 / 多线程分支工作」，也会触发。任务看起来大、可并行、可按分支隔离时，Codex 可以**建议**该模式，但协议规定**不得在未获确认时创建 worker**。

### 4.2 一次完整运行

| 步骤 | 用户看到什么 | 实际产物 |
| --- | --- | --- |
| 1. 可行性评估 | leader 说明拆分方案、worker 数量、模型配置来源 | 判断结论（可能直接建议单线程） |
| 2. 一次授权确认 | 一次核对：拆分、新会话/worktree、配置来源、消息范围、提交、串行集成、替换/清理 | 授权范围与来源写入状态 |
| 3. 预检 | 能力探测 + Git 检查 + 项目唯一匹配 + 写权限 | 预检证据写入状态 |
| 4. 建 worker | 每个 worker 拿到独立 worktree 与分支，先只做启动核验 | `planned → creating → pending → validating → ready` |
| 5. 派发 | 每个 worker 收到自包含任务书 + 完整花名册 | `ready → dispatched` |
| 6. 执行观察 | 用户通常无需介入；有阻塞才被叫 | worker 侧 `.threadweave/notes.md` / `report.md` |
| 7. 串行合并 | 逐分支审查、必要时返工、合并、跑验证 | `integrationLog` 逐条记录 |
| 8. 最终复查与清理 | 汇总报告：合并结果、验证结论、清理状态 | `final-report.md` + `state.json` 终态 |

授权之后整轮是自主的；用户可以随时要状态或中止。

### 4.3 状态目录与恢复

```
<repo>/.threadweave/
└── <run-id>/
    ├── state.json              # 机器可读权威状态（schema 校验 + 原子写 + revision）
    ├── state.md                # 人类可读运行日志（协议要求）
    ├── archive-manifest.json   # 归档文件的 SHA256 清单
    ├── reports/
    │   ├── <role>/<attempt>/<revision>/   # worker 报告与 notes 归档
    │   └── final-report.md
    └── archive.lock
```

关键规则：

- 目录通过 `git rev-parse --git-path info/exclude` 加入排除，**永不提交**，运行结束后保留作审计记录。
- `.threadweave` 与 run 目录都不允许是符号链接（`state_store.run_state_dir` 强制检查）。
- 写入前校验 `runId` 与目录一致；磁盘 revision 与内存 revision 不一致时抛 `StaleStateError`，拒绝覆盖。
- 上下文被压缩或中断后，leader **必须先重读状态文件再行动**。

本地只读诊断命令：

```bash
python3 scripts/threadweave.py preflight --repo .
python3 scripts/threadweave.py status --repo .
python3 scripts/threadweave.py inspect --repo .
python3 scripts/threadweave.py doctor --repo .
python3 scripts/threadweave.py cleanup-plan --repo . --run <run-id> --observations <file>
```

- `status` 会定位「最近一个仍需关注」的 run；`failed` / `aborted` 但清理未完成的 run 仍会被返回。
- `cleanup-plan` 只输出计划，不执行任何删除。

### 4.4 故障处置矩阵

| 故障 | 判定依据 | 处置 |
| --- | --- | --- |
| 初始化超时 | 超过 `initializationTimeoutSeconds`（默认 300 秒） | 先查操作状态，**超时不等于已停止**；无法确认则停止新建并上报未决资源 |
| worker 无活动 | 360 秒无进展 | 请求状态；再给 120 秒宽限，期间核对长命令与依赖 |
| 确认停止 | 三项证据齐全：线程 idle、有最终答复、无活跃 turn | 才写 `stopStatus=confirmed` 并绑定当前 `activityRevision` |
| 需要换人 | 停止证据已确认 + 无后续 attempt + 未超替换上限 | `replace_worker` 返回 `nextAttempt`；新 attempt 走全新分支/worktree 并重过启动门禁 |
| 派发结果不明 | `dispatchIntent.result` 为 `pending` / `unknown` | 先核对（`sent` / `not_sent` / `unknown`），确认已发送则推进 `dispatched`，确认未发送才允许重试，仍不明则保持未决 |
| 启动报告不合格 | 6 项门禁任一失败，或证据超过 300 秒 | 禁止派发；修复后重新核验 |
| 集成验证失败 | `verification` 以 `FAIL` 开头 | 记 `integrationLog.result=failed` 并抛错，**不得继续合并下一条分支** |
| 报告与分支不符 | threadId / branch / head / reportSha / taskRevision 任一不匹配 | 拒绝接收，退回核对 |
| 状态落后 | 磁盘 revision 与内存 revision 不一致 | 抛 `StaleStateError`，重新读取后再改 |

### 4.5 收尾与清理

清理是**分类 → 判断 → 才动作**，任何一步证据不足就不动：

| 对象 | 保护条件（满足任一即保留） | 允许清理的条件 |
| --- | --- | --- |
| worktree | 存在性未知、共享、primary、非本 run 所有、脏、有未合并提交、报告未归档、停止未验证、worker 非 idle/archived | 以上全部通过，dir 干净、无未合并提交、报告已归档校验 |
| 分支 | 存在性未知、非本 run 所有、仍被 checkout、未合入集成分支 | 已合入集成分支 |
| 报告源文件 | 归档未校验 | 已归档且校验通过 |
| automation | 非本 run 创建 | 本 run 创建 |

终止语义：`aborted` 与清理状态分开记录；初始化失败记 `failed`；存在未决资源时**不得报告完整完成**。

### 4.6 当前宿主边界（实测）

| 能力 | 结论 |
| --- | --- |
| `create_thread` / `send_message_to_thread` / `read_thread` / `wait_threads` / `set_thread_archived` / `create_worktree` | 支持 |
| 异步创建解析 | 支持：`create_thread` 返回 `clientThreadId`，通过 `list_threads` 按精确元数据解析真实 `threadId` |
| `attach_worktree` | 部分支持：对自身 managed worktree 幂等成功；对 worker 所属 worktree 报「owned by another task」 |
| `archive_worktree` | 部分支持：非 primary worktree 成功；primary checkout 拒绝 |
| 创建超时 | 不支持：`create_thread` schema 无 timeout 参数，只能在适配器层构造 |
| 取消 | 受限：是 turn 边界 steering，不会立即中断当前命令 |
| 不可用模型 / 非法 reasoning | 创建前明确阻塞，不会静默替换 |

## 5. 技术路线

### 5.1 分层

```
┌──────────────────────────────────────────────┐
│ Leader（Codex 模型，当前会话）                 │
│   按 SKILL.md 六阶段执行，做判断与取舍          │
└───────────────┬──────────────────────────────┘
                │ 读模板 / 调用本地逻辑 / 调用宿主工具
┌───────────────┴──────────────────────────────┐
│ 协议层：SKILL.md + references/*.md            │  ← 真正的"程序"
├──────────────────────────────────────────────┤
│ 本地逻辑层：scripts/*.py（纯函数 + 状态机）     │  ← 可测试的判定
├──────────────────────────────────────────────┤
│ 状态层：.threadweave/<run>/state.json          │  ← durable 事实
├──────────────────────────────────────────────┤
│ 宿主动作层：create_thread / send_message / ... │  ← 由 leader 直接调用
└──────────────────────────────────────────────┘
```

注意 `HostAdapter` 的位置：它是**给未来真实适配器预留的缝**，当前只有抽象类与默认拒绝实现，没有接任何真实 API。也就是说「本地逻辑层」与「宿主动作层」之间目前是**断开的**，实际连接由 leader 自己完成。

### 5.2 关键设计决策

| 决策 | 理由 | 代价 |
| --- | --- | --- |
| 用真实线程而不是 subagent | worker 需要独立上下文、独立配置、可中途通信、可归档替换 | 强依赖宿主能力，换宿主即失效 |
| 一 worker 一 worktree 一分支 | 共享 checkout 会静默串改，是最常见死法 | 每个 worker 有创建与清理成本 |
| 大内容走文件、消息只带信号 | leader 上下文是全队最稀缺资源，转录常驻不可回收 | 协议更啰嗦，leader 要多做文件读写 |
| 状态立即落盘 + revision 校验 | 长任务会跨上下文压缩、跨会话中断 | 每次变更一次 IO；并发写入需处理冲突 |
| 串行合并 + 逐分支验证 | 缺陷与回归才能归因到具体 worker | 并行度只体现在「实现阶段」，合并阶段串行 |
| 派发前先持久化 intent | 消息可能发成功但调用方看到异常，重发会造成重复实施 | 需要额外的核对流程 |
| 清理只分类不执行 | 误删 worktree / 未合并分支是不可逆损失 | 人工或 leader 需二次确认才真正删除 |
| 纯标准库实现 | 零依赖、易审计、可在任意 Python 3 环境跑 | 无类型检查、无异步、锁依赖 POSIX `fcntl` |

### 5.3 状态机

run 状态：

```
planned → preflight → initializing → dispatching
        → observing → integrating → final-review
        → complete | cleanup_pending
任意非终态 → failed | aborted
```

worker 状态：

```
planned → creating → pending → validating → ready
        → dispatched → running ⇄ blocked → reported
        → integrated → archived
任意未完成态 → failed | cancelled
```

约束：

- `integrated` 必须同时满足「已有被接受的报告」+「集成日志中该分支结果为 `merged`」。
- `complete` 必须满足「`finalReview=complete`」+「`cleanup=complete`」+「所有当前有效 worker 已 integrated/archived」+「无未决资源」。
- 每个角色只取 attempt 最大的 worker 作为有效记录；历史 attempt 保留审计，但不阻塞完成判定。
- 同态写入视为幂等。

### 5.4 验证方式

| 层次 | 方式 | 当前结果 |
| --- | --- | --- |
| 单元/契约 | 14 套 smoke 脚本，`python3 tests/run_all.py` | **327 项断言通过** |
| 故障注入 | fake adapter：不可用模型、非法 reasoning、零 projectId、创建超时、取消、停滞、替换 | 已覆盖 |
| 真实正向 | 双 worker 端到端：创建 → 初始化 → 消息 → 提交 → 串行集成 → 报告 → 清理 | 1 次（`20261112-real-dual-02`） |
| 真实故障 | 停滞、替换、managed worktree 生命周期 | 部分覆盖 |
| CI | GitHub Actions 跑 `tests/run_all.py` | 已配置 |

### 5.5 成本结构

- **固定成本**：预检 + 建线程 + 每个 worker 的任务设计与派发 + 每分支审查与合并验证 + 最终整体复查。
- **可变成本**：worker 数量。协议明确要求「一个真正独立的工作面配一个 worker，不多配」。
- **隐性成本**：宿主 schema 变化后要重跑真实 smoke 并更新兼容矩阵；这是持续的维护税。
- **失败成本**：大部分失败模式被设计成「停下并保留资源」，而不是「自动重试」。这保护了数据，但需要人介入。

## 6. 投入判断依据

### 6.1 已经成立的价值

1. **失败模式被系统性地命名并配对护栏**，这是多数多 agent 方案缺的部分。尤其是「共享 checkout」「上下文经济」「串行合并归因」「派发不确定」四条，都是实际会踩且难事后补救的坑。
2. **协议可审计**：每次状态变更落盘、每个 worker 有独立分支与报告、每次合并有验证记录。出问题能回溯到具体角色与具体 revision。
3. **本地逻辑层可测试**：327 项断言覆盖状态转换、门禁、恢复、清理分类、并发锁、故障路径。这部分即使脱离 Codex 也有复用价值。
4. **零依赖、易分发**：一个克隆 + 重启即可用；不引入服务、数据库、密钥。

### 6.2 结构性约束（决定天花板的事实）

1. **运行时不经过代码。** 真正执行流程的是模型读 `SKILL.md`。代码能阻止非法状态落盘，但阻止不了模型跳过某个阶段——除非把整个流程搬进代码。
2. **能力绑定单一宿主。** 依赖真实线程、worktree、线程间消息。换到不支持这些的宿主，整套协议直接失效；而宿主 schema 会变，兼容矩阵需要持续维护。
3. **收益有明确门槛。** 少于 3 个真正独立的工作面时，固定开销大概率吃掉并行收益。
4. **合并阶段天然串行。** 并行只发生在「实现」，不发生在「集成」。任务本身依赖链长时，加速有限。
5. **分发形态限制了想象空间。** 它是 skill（文档 + 脚本），不是产品。非 Codex 用户无法直接使用，也难以做成收费能力。

### 6.3 三条可选路径

| 路径 | 做什么 | 成本 | 收益 | 风险 | 何时选 |
| --- | --- | --- | --- | --- | --- |
| A. 协议打磨 | 只维护 `SKILL.md` 与模板，按实际使用中的翻车点补条款 | 低（每次几小时） | 作为个人工作流够用；认知负担最低 | 边际收益递减，问题仍靠模型自觉 | 每月实际使用 ≥1 次、任务形态稳定 |
| B. 补真实适配器 | 实现一个真实 `HostAdapter`，让 `controller.py` 真正驱动「建线程 → 派发 → 收报告 → 集成」，并用一个端到端 run 验证 | 中（数天到两周） | 把参考实现变成可执行编排器，协议漂移可被代码拦住 | 宿主 API 变更即需维护；可能与宿主内建能力重复 | 你希望它稳定复用、且能接受维护税 |
| C. 通用编排层 | 抽出与宿主无关的多 agent 调度层，支持多种 agent 后端 | 高（数月） | 潜在产品化 | 失去「Codex 原生线程」这个唯一差异化，进入红海 | 有明确的外部用户与商业假设 |

### 6.4 我的建议

**如果继续投入，选 B 的最小切片，而不是继续给协议加条款。**

理由：

- A 已经进入收益递减区：协议文本再细，也无法阻止模型跳过步骤；真正的增量来自「关键动作有代码兜底」。
- C 的前提（外部用户、跨宿主需求）目前没有证据支撑，且会丢掉唯一护城河。
- B 的最小切片可以很小、也可验证：只接 4 个动作（`create_worker` / `send_message` / `read_thread` / `wait_threads`）+ 1 个真实端到端 run，就能把「派发不确定」「启动门禁」「串行集成」这三条最贵的护栏从「靠自觉」变成「跑不过就报错」。

**不建议继续投入的信号**（满足任意两条就该停）：

- 过去一个月实际使用少于 2 次。
- 你的任务多数是单文件或紧耦合改造，拆分后合并成本高于收益。
- 每次使用后都需要人工修状态文件或手工收尾。
- 宿主升级频繁，而你每月花在重跑 smoke 与更新兼容矩阵上的时间超过实际收益。

## 7. 下一步（若选 B）

按依赖顺序，每步都可独立验收：

1. **真实适配器最小实现**：基于当前 Codex 工具实现 `create_worker` / `send_message` / `read_thread` / `wait_threads`，其余方法先显式抛错。
   验收：用 fake 与真实各跑一次，`capability_snapshot()` 记录真实能力。
2. **CLI 驱动单条链路**：`threadweave.py` 增加 `dispatch` / `accept-report` / `integrate` 三个子命令，全部走 `Controller` 与 `state_store`。
   验收：一条命令能从 `ready` 推进到 `dispatched`，且重复执行不产生第二次发送。
3. **端到端真实 run**：两个 worker、两个 worktree、一次串行集成。
   验收：状态机全程合法、`integrationLog` 有两条 `merged`、清理计划全部为 `remove`/`already_removed`。
4. **失败注入对照**：在真实链路上复现「发送抛异常但消息已送达」，验证 `resolve_dispatch` 不重复派发。
   验收：同一 `taskRevision` 只出现一次 `dispatchAt`。
5. **把结果写回兼容矩阵**：只记录实测结论，未验证项保持「未知」。

完成 1–3 之后，再判断是否值得做第 4–5 步；若第 1 步就发现宿主 API 不稳定，及时停在 A。
