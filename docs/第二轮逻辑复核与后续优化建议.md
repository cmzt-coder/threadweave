当前运行链路仍是：任务分析与授权 → preflight → 项目唯一匹配 → worker 创建与初始化 → 团队启动门禁 → 正式派发 → 观察、停止、返工和替换 → 串行审查集成 → 归档与清理。

上一轮三批优化已有对应提交：

- `41809d5`、`30f8a24`：schema 校验、revision 冲突检查、派发意图、团队门禁与输入边界测试。
- `b371f56`：停止请求/确认、返工、按 attempt/revision 归档、停滞宽限及诊断入口。
- `31de08d`：按 host 匹配项目、能力快照、支持时传递创建 timeout。

本轮全量测试：`python3 tests/run_all.py`，**14 套 smoke、261 项断言全部通过**。

复核发现，部分上一轮验收条件仍未完整覆盖，主要集中在入口之间共用的约束、状态变化后的证据有效性，以及并发和中断后的事务恢复。下文将其登记为本次 N01–N08，保留原审查文档作为历史记录。

现有 `docs/待办存档-2026-11-12.md` 已登记 L13（启动 root 精确比较）和 L14（真实 HostAdapter）。它们是已知边界；本报告补充其前置条件和相关断点。

本轮探针只使用临时目录、fake adapter、线程屏障与故障注入。没有新建真实 Codex worker、调用真实消息接口、删除 worktree 或核验远端状态。清理探针检查的是建议动作，没有执行动作。

## 二、应优先收敛的逻辑

### N01 · P1：把“是否允许产生外部动作”设为所有入口的共同约束

位置：`scripts/controller.py:71`、`scripts/controller.py:139`、`scripts/controller.py:198`。

**已复现：**

1. adapter 发送时抛 TimeoutError，控制器保存 dispatchIntent.result=unknown，worker 仍为 ready。直接再次调用 dispatch，旧 intent 被覆盖，并发生第二次发送。
2. run.status=aborted 且目标 worker ready，dispatch 仍发送消息。
3. 对 ready worker 执行 request_stop 后，再调用 dispatch，仍发送消息。
4. 给控制器提供不完整且 status=aborted 的状态，调用 create_worker，adapter 仍被调用，且没有创建状态文件。

恢复分类器对 unknown 返回 revalidate，尚不能防止调用方绕过恢复分类器直接调用派发入口。

**建议：**

- 创建、初次派发、返工派发、替换共用动作前置检查：run 阶段、授权范围、状态有效性、角色身份、停止标记、未决操作和预算。
- pending/unknown 派发意图必须先通过独立核对操作收敛，不允许普通 dispatch 覆盖。
- 外部调用前保存唯一操作 ID 和身份；同一任务重试保持同一 ID。当前 dispatchId 以秒为粒度，未进入发送给 worker 的消息，尚无法用于确认与去重。
- 将主动取消后的禁止新任务作为 run 级约束，停止确认与资源保全继续单独推进。

**验收：** aborted/failed/complete、停止中、存在未决派发、无效状态时，所有外部创建与任务消息调用数均为零；结果不明必须先核对，不能用新 ID 静默覆盖。

### N02 · P1：区分历史 attempt、当前有效 worker 和已经通过的团队门禁

位置：`scripts/controller.py:100`。

**已复现：**

- 同角色保留 a#1=cancelled，并新增 a#2=ready，派发 a#2 被旧 a#1 阻塞：`team gate not ready: a#1:cancelled`。
- A 已派发并进入 running、B 仍 ready，派发 B 被 A 阻塞：`team gate not ready: a#1:running`。

目前门禁遍历全部历史记录，允许 dispatched/reported，却不允许 running。已有 A→B 测试只覆盖 A 仍处于 dispatched 的情况。

**建议：**

- 为每个角色显式记录当前选定 attempt；历史失败/取消记录继续保留审计，门禁只检查本轮有效花名册。
- 首次派发前持久化“团队初始化已通过”的门禁记录，绑定 roster revision 和基线。
- 后续派发验证门禁记录与目标 worker，不要求其他已开工 worker 回到初始化状态；替换时重新验证新 attempt 并更新花名册版本。
- 同一角色不能同时有两个可执行 attempt；替换计划必须有持久化的预留，避免两个调用者同时生成同一替代者。

**验收：** A running 时 B 可派发；旧 attempt 保留时替代者可派发；新增未验证的有效 worker 会使相应门禁失效；同角色并发替换只能有一个有效操作。

### N03 · P1：启动和停止证据应绑定持久身份与活动轮次

位置：`scripts/controller.py:71`、`scripts/controller.py:147`、`scripts/startup_gate.py:12`。

**已复现：** 持久状态里的 worker.branch=tw/a-1，同时把 startup_report.branch 与 expected.branch 都填为 wrong-branch，dispatch 校验通过并发送消息。落盘的 worker 分支与 startupEvidence 分支不同。

当前检查主要验证调用方提供的两份数据彼此一致，未完整对照持久状态。role、attempt、observedAt 可省略；expected.other_roots 也由调用方提供。精确 root 比较已有 L13 待办。

**已复现补充：** confirm_stop 保存的布尔确认没有活动轮次；rework 将 worker 改回 running 时，没有使旧 stopStatus=confirmed 失效。随后调用 replace_worker，仍可取得 nextAttempt=2 的替换计划。本轮未创建真实替代 worker。

**建议：**

- 由持久 run/worker 身份生成 expected：project/host/thread、role/attempt、branch、base、精确 root 和其他有效根目录。
- 观察证据带采集时间、来源与 roster/activity revision；拒绝未来时间、缺失时间、身份不符和过期证据。
- 重新派发、返工或观察到新活动后，使旧停止证明失效；停止确认必须针对当前活动轮次。
- 派发前对集成 HEAD 的检查接真实 Git 观察，不能仅信任调用方填入的 integration_head。

**验收：** 报告与 expected 相互一致但违背持久身份时零消息；不同 root、同 root 的两个 worker、旧停止证明和未来时间均被拒绝。

### N04 · P1：把状态保存做成失败后可继续恢复的提交过程

位置：`scripts/controller.py:33`、`scripts/state_schema.py:72`、`scripts/state_store.py:110`。

**已复现：**

- 首次成功保存后 disk revision=1。注入底层 write_state_atomic 失败，memory revision 先变成 2；解除故障再次 save，因 disk=1、memory=2 抛 StaleStateError。
- Controller 的目录 run_id 与 state.runId 不一致，仍可保存。
- run=complete、finalReview/cleanup 都标 complete，但 worker=running 且 outstandingResources 非空，validate_state 仍接受。

现有写入失败测试通过覆盖整个 save 注入异常，未覆盖真实 save 内部已修改 revision 后的失败窗口。

**建议：**

- 在锁内基于最新已提交状态创建候选副本，验证身份、转换和不变量，原子写入成功后再替换内存；写入失败不消耗 revision。
- 校验目录 runId、持久 runId、控制器项目与仓库身份一致；检测磁盘丢失、损坏或版本不支持。
- 完成态要求无未决创建/派发、无活跃有效 worker、无 outstandingResources，并校验清理和资源记录一致。
- 对写入成功但调用方结果不明的情况，以重新读取和 revision/操作 ID 核对收敛。

**验收：** 真实底层写入失败后可重读并恢复；旧快照仍被拒绝；run 身份不一致和虚假完成不能落盘。

### N05 · P1：归档应保证文件与 manifest 一起可恢复

位置：`scripts/archival.py:45`、`scripts/archival.py:81`。

**已复现：**

- 两个归档调用用屏障同步到读取旧 manifest，均正常完成；磁盘保留两个 report.md，最终 manifest 只有一条记录。
- 注入 copy2 写入部分目标后抛 OSError；再次归档相同源文件，被遗留的半成品触发 ArchiveConflict。

按 attempt/revision 隔离已经实现，manifest 的读改写仍未加锁，复制仍直接写最终文件。

**建议：**

- 同一 run 的 manifest 在排他锁内合并；文件先复制到临时目标，完成哈希校验后原子发布。
- 区分“未提交半成品”和“已提交且内容不同的证据”；前者可安全重试，后者继续拒绝覆盖。
- manifest 成功提交后才将证据标为可用于清理；源文件变化时拒绝把不一致哈希当作已完成归档。

**验收：** 并发归档所有条目保留；复制中断、来源变化、manifest 写入失败后可恢复；目标与 manifest 校验一致才允许清理。

## 四、下一轮推荐范围与验收场景

建议先安排一轮“跨模块闭环验收”，优先处理 N01–N05，并把 N06/N07 中会影响替换和清理决策的条件一并验证。L13 可在证据绑定中完成；L14 的真实接入放在本地闭环稳定后。

| 场景 | 动作的准确触发条件 | 必须观察到的结果 |
| --- | --- | --- |
| 发送结果不明 | 持久 intent 为 pending/unknown | 普通派发拒绝；先核对旧操作，不增加发送次数 |
| 运行取消或停止中 | run 已 aborted 或目标 stopStatus=requested | 禁止创建与正式派发；允许观察、保全与受保护清理 |
| A 先进入执行 | 全团队启动门禁已通过，A running，B ready | B 仍能获得唯一一次正式派发 |
| 保留旧 attempt | a#1 cancelled 且停止已确认，选定 a#2 ready | 旧记录保留；a#2 的门禁按有效花名册判断 |
| 返工后再次活动 | 新任务修订或新进展已出现 | 旧停止证明失效；旧宽限取消；重新采集停止证据 |
| 写入失败 | 候选状态验证通过，底层写入失败 | 内存和 revision 不冒充已提交；重读后可继续恢复 |
| 两份报告并发 | 两个不同身份/attempt 的证据同时归档 | 文件和 manifest 均完整，无丢条目 |
| 归档中断 | 临时复制或 manifest 提交中途失败 | 可以重试；已提交证据不被覆盖，半成品不冒充归档 |
| 完成态校验 | 声称 complete | 无活跃有效 worker、未决外部操作或清理债务 |
| 诊断与恢复 | JSON 可读但结构/身份/版本有误 | 明确诊断，不返回健康，不直接进入执行 |

测试应通过同一个控制器/状态入口串起多个阶段，并注入故障后重新构造控制器读取磁盘状态。分别测试多进程竞争、崩溃窗口和正常恢复；单个纯函数断言继续保留。

## 五、正确性收敛后的新增优化方向

1. **可观测性与运行复盘**：从真实事件统计创建/初始化、执行、返工、审查、合并和清理耗时，以及消息/读取次数、残留资源和 leader 介入次数。成本只统计宿主实际提供的数据。
2. **任务拆分与资源预算**：用运行数据评估团队模式的收益，调整 worker 数量和任务边界；明确依赖与文件所有权，先做可审查的调度计划，不自动扩大并发。
3. **状态版本与兼容维护**：新增字段需有版本策略、旧状态读取或迁移方案、只读诊断和回滚说明；工具 schema 有变化时生成差异报告与所需 smoke 清单。

多仓库、PR 自动化、可视化与产品化继续保留为待评估方向。当前建议先完成上述可本地复现的闭环验收，再确定新的功能范围。
