# Threadweave 第三轮核心功能逻辑审查与优化建议

日期：2026-11-12。
基线：`412bb8d8a48de70488a17bab5ac6f7d4daff157d`。
性质：重新熟悉两轮改造后的代码与协议，复核核心链路；本轮仅形成建议，不实施功能修改。

## 一、核心功能边界

用户本轮明确要求：**所有优化逻辑都要忠实于项目的核心功能。**

本报告仅围绕以下链路提出建议：

1. leader 分析任务、明确边界与授权。
2. 创建真实 Codex worker 线程，每个 worker 使用独立 worktree 与分支。
3. 完成启动核验，发送自包含任务，进行范围内协作与进展观察。
4. 对故障执行核对、停止、返工或有上限的替换。
5. leader 收集报告、审查产出、逐分支串行集成并验证。
6. 保全报告与成果，安全清理，确认整轮完成或中止。

优化应提高这条链路的正确性、可恢复性与使用效率。当前建议不引入通用调度平台、额外服务、可视化、多仓库或新的协作产品形态。

## 三、核心链路中的剩余优化

### T01 · 优先修复：让“派发结果核对”真正恢复执行状态

核心关联：消息结果不明后，leader 能继续同一任务，避免重复实施。

位置：`scripts/controller.py:213`、`references/state.schema.json`。

**实际复现：**

- 先让 adapter 在发送时抛 TimeoutError，磁盘保存 dispatchIntent.result=unknown。
- 从磁盘重建控制器，再分别调用 resolve_dispatch(..., 'sent') 和 resolve_dispatch(..., 'not_sent')。
- 两种结果都因 `dispatchIntent: unexpected resolvedAt` 被 schema 拒绝，磁盘仍是 unknown。

原因是核对方法新增 resolvedAt，而 schema 未声明该字段。

同时，从当前方法代码可见，它只修改 intent 的结果，没有同步 worker 的执行状态。需要把核对结果与 worker 状态、活动轮次一起定义，避免修复字段后留下新的重复派发窗口。

**建议的准确动作条件：**

| 核对结果 | 允许的动作 |
| --- | --- |
| 确认已发送且证据匹配本任务 | 原子记录证据与发送结果，将 ready/pending 意图对应的任务推进到已派发；继续观察，不再发送同一任务 |
| 确认未发送 | 记录确定未送达证据，允许受控重试；保留原任务身份和历史核对记录 |
| 仍无法确认 | 保持未决状态，继续核对；不创建新的派发意图覆盖旧记录 |

任务消息和报告携带可匹配的 run/role/attempt/task revision/dispatch ID。消息仍保持短小，完整报告继续以文件承载。

验收：通过真实控制器入口完成“发送异常 → 从磁盘恢复 → 核对 → 继续观察或受控重试”，同时验证零重复任务和核对记录可保存。

### T02 · 优先修复：统一“当前有效 worker”与整轮完成规则

核心关联：worker 可以被安全替换，替换后的团队仍能完成任务，同时保留旧成果与审计。

位置：`scripts/controller.py:76`、`scripts/controller.py:99`、`scripts/state_schema.py:72`。

**实际复现：**

- a#1 已 cancelled，停止已确认；a#2 已 archived，最终审查和清理均完成。
- 将 run 标为 complete，仍因“全部 worker 必须 integrated/archived”被拒绝。当前完成校验把历史取消 attempt 也当作必须集成的成员。
- 若 a#1 和 a#2 均被保留为 ready，虽然有效视图选中 a#2，直接指定 dispatch(a, 1, ...) 仍会给旧 a#1 发送任务。

第二种情形是未被当前不变量禁止的冲突状态；本轮仅在临时状态中构造，没有创建真实重复 worker。

**建议：**

- 正式派发只接受当前选定 attempt；历史记录继续保留，但不能重新执行任务。
- 当前有效 attempt 参与任务完成判定；所有历史 attempt 继续参与停止、资源保全和清理判定。
- run 完成要求：所有选定产出已审查集成或有明确获准的处置；所有退役 attempt 已确认停止；所有资源已处理且无未决操作。
- 替换预算、资源预留和有效 attempt 切换使用同一次受保护状态更新；重复请求不能预留两个替代者。

验收：完整跑通“a#1 失败并保全 → 停止确认 → a#2 启动、实施、报告、集成 → 清理 → run complete”；旧 attempt 的迟到消息或旧派发请求不能改变当前任务结果。

### T03 · 优先修复：独立 worktree 校验应自动使用已登记身份

核心关联：每个真实 worker 始终在分配给自己的 worktree 中实施。

位置：`scripts/controller.py:99`、`scripts/startup_gate.py:31`。

**实际复现：**

- state.workers 中登记的 worktree 为 a 目录。
- startup_report 报告另一个 unregistered-root，调用时未填写 expected.worker_root。
- 控制器接受报告并发送消息，持久化 worktree 与 startupEvidence.worktree_root 出现不一致。
- observedAt 设置为未来时间 `2099-01-01T00:00:00+00:00`，也会通过现有年龄检查。

精确 root 比较已实现为纯函数的可选条件；控制器还需要保证该条件来自持久 worker 记录并必定执行。

**建议：**

- 从已登记的 worker.worktree、project.commonDirectory、有效花名册和 leader 根目录生成预期身份。
- root 未登记或线程与目录绑定尚未核实时，保持 validating，禁止正式派发。
- 拒绝时间缺失、无法解析、明显在未来和超过有效期的证据；保存采集时间与来源。
- 正式派发前获取当前 Git 事实，由 leader 核验目录、仓库、分支、基线与隔离；任务消息沿用现有自检要求。

验收：调用方省略 expected.worker_root 也不能跳过精确目录比较；错误仓库、共享 root、未登记 root 和未来时间均产生零任务消息。

### T04 · 下一阶段：把“报告 → leader 审查 → 串行集成”串成同一验收链

核心关联：worker 的产出经过 leader 审查后逐个进入集成分支，每次集成均可归因。

位置：`SKILL.md` 第四至六阶段、`references/worker-report-template.md`、`scripts/controller.py:93`。

当前协议已规定报告、SHA、分支范围、leader 审查和逐次验证；控制器主要仍提供状态转换。

**实际复现：** reported worker 可以直接 transition_worker(..., 'integrated')，即使 integrationLog 为空；随后只把最终审查与清理标签置为 complete，状态校验仍接受 run complete。本轮没有实际执行 Git merge。

**建议补充最小验收动作：**

1. 收集报告时，核对 run/role/attempt/task revision、报告路径与 SHA，隔离旧 attempt 和旧返工修订的迟到报告。
2. leader 对照正式派发的文件范围、共享契约和验收标准审查 diff，记录结论；需要返工则生成新的明确修订。
3. 集成前核对 branch tip、base 祖先关系、停止证据、集成 checkout clean 与预定合并顺序。
4. 每次记录集成前/后 SHA、leader 审查结论、实际合并结果及验证结果；本分支验证失败时停止下一分支。
5. 最终完成校验关联这些记录，防止单独改变状态标签绕过核心步骤。

这些辅助动作只校验身份、Git 事实与流程证据；代码语义审查、冲突处理和团队决策继续由 leader 负责。

**同时补齐阶段约束：** 临时探针中，cleanup_pending 的 run 仍可正式派发；缺少 authorization 的状态也能经 create_worker 调用 adapter 且没有先落盘。应按六阶段明确创建、派发、返工、集成与清理各自允许的阶段，并在产生外部动作前完成相应检查和记录。

验收：正常 A→B 集成、A 验证失败阻止 B、报告 SHA 不匹配、越界文件、旧报告迟到、集成后中断恢复分别有明确处理结果。

### T05 · 随后收敛：停滞判断只依据当前阶段的有效进展

核心关联：leader 准确判断何时催问、等待或替换 worker。

位置：`scripts/budget.py:15`、`scripts/budget.py:25`、`scripts/recovery.py:9`。

**实际复现：**

- 10:07 请求状态，graceDeadline 为 10:10；worker 10:11 出现新进展，10:12 检查仍返回 stalled，因为代码先处理旧 graceDeadline。
- worker 已 running，创建十二分钟后仍会得到 initialization deadline_exceeded。

从当前恢复代码可见，reported 已使用报告 SHA 和祖先关系，但 running/blocked 仍进入 HEAD == base 的判断；正常执行中已有提交时也需要阶段化处理。

**建议：**

- 先判断新进展是否已使旧请求/宽限失效，再判断宽限期限。
- 初始化预算仅针对 creating/pending/validating 等初始化状态；执行预算和无进展判断单独计算。
- 执行中恢复检查允许经核验的正常提交或 WIP，先保全并让 leader 审查，再决定继续、等待或替换。

验收：长任务正常执行不被初始化超时干扰；新进展取消旧宽限；执行中断且已有提交时可进入核验和恢复，不被启动规则一律阻塞。

### T06 · 已有边界继续推进：真实宿主接入与 Skill 状态一致

核心关联：用户实际使用 Skill 时，能够调用已有保障并在中断后定位同一轮任务。

当前 L14 真实 HostAdapter 仍待接入。教程声明 state.json 为机器状态源，Skill 与 leader 模板仍要求写 state.md，尚需统一实际写入与恢复路径。

**建议：** 在 T01–T05 的本地核心链路收敛后，选择当前宿主明确支持的工具调用方式，桥接既有 create/message/read/wait/worktree 能力；建立可回读的状态入口，Markdown 保持简洁的人类可读视图。

Codex 更新维护只核对本项目依赖的工具参数、返回身份、线程/worktree 行为和模型配置来源；按变化重跑相关契约与真实 smoke，记录支持、受限或未知。保持现有授权与能力边界。

验收：真实双 worker 完成一次正向链路，并覆盖一次中断恢复、返工或替换；恢复前后操作 ID、有效 worker、报告与 Git 结果一致。不得以 fake adapter 通过替代真实宿主证据。

## 四、推荐顺序与停止扩展的标准

1. **先完成 T01–T03 的回归修复**：派发结果可核对、替换后能收尾、worktree 身份不可绕过。
2. **再完成 T04–T05 的核心链路验收**：leader 报告审查与串行集成有一致记录，停滞与恢复按阶段处理。
3. **最后推进已有 T06/L14**：连接真实宿主，验证 Skill 实际运行能使用前述保障。

每项验收必须通过真实入口串起多个阶段，并在故障后重新加载磁盘状态继续，不能只检查某个新增字段或单个纯函数。

本轮建议完成后，以正常双 worker、派发不明恢复、替换、返工、合并失败停止和安全清理六类场景作为核心回归集合。核心回归稳定后，后续优化应由实际运行缺陷或效率数据驱动。

本轮仅新增本报告，未修改功能代码、未新建真实 worker、未提交或推送。已有历史报告和待办未改写。
