# Threadweave 项目逻辑审查与优化建议

日期：2026-11-12。
审查基线：`d9bc9de38e88dfbf9d2893e469124e340d7757d1`。
性质：代码与协议审查、临时故障复现、下一轮方案建议；以下建议尚未实施。

## 一、结论与审查边界

当前项目具有六阶段协作协议、真实双 worker 运行记录、Python 参考模块和本地测试。下一轮最有价值的工作，是将协议中的启动、恢复、停止和清理约束落实到可执行入口，再连接真实宿主适配器。

当前实际执行仍依赖 leader 按 Skill 编排。`Controller` 是骨架，`HostAdapter` 没有真实宿主实现，CLI 只检查本地条件、读取状态和生成清理计划。下文发现的模块问题不代表历史真实冒烟失败，也不表示本轮发生过重复派发或数据删除。

本轮阅读了 Skill、主要模板、全部 Python 运行模块、测试和项目文档；重跑本地测试，并用临时目录与 fake adapter 验证边界。本轮未创建真实 worker、未执行清理、未修改业务代码，也未核验新的 Codex 版本或远端状态。

审查开始时基线为 `9709ca6`，期间出现新增提交 `558a232`、`d9bc9de`，已阅读新增模块与测试，并按 `d9bc9de` 重新运行测试。最新结果为 **13 套 smoke、201 项断言全部通过**。部分故障探针仍能复现下列缺口，说明现有测试覆盖的是既有用例，尚未覆盖全部协议约束。

## 二、功能节点与应执行的触发条件

下表是建议形成的统一执行契约；“缺口”描述当前代码与该契约的差异。

| 节点 | 应触发动作的准确条件 | 当前实现与缺口 |
| --- | --- | --- |
| 项目解析 | canonical 仓库根、目标 host、Git 标记均匹配，且恰好一项并具有有效 projectId | 新解析器检查路径与 Git 标记，但没有 host 参数，也未拒绝缺失 projectId |
| 创建 worker | 已有用户授权、preflight 通过、创建意图和 attempt 已持久化、无身份未明的旧操作 | Skill 有约束；控制器创建方法直接调用 adapter |
| 解析 pending | 存在宿主明确支持的解析路径；实际结果能确定真实 threadId | Skill 有约束；接口尚无规范化 pending 结果与解析入口 |
| 标记 ready | leader 已核验仓库、独占目录、分支、精确基线、clean，并保存证据 | 转换表仅验证状态边，不检查证据 |
| 首次正式派发 | 本轮所有选定 worker 均通过门禁；目标 ready；run 阶段允许；集成 HEAD 未漂移 | 控制器只检查目标 ready 和非空 threadId，启动报告可以省略 |
| 后续正式派发 | 团队启动门禁已通过；目标尚未派发；前一 worker 已派发不应令团队门禁失效 | 需记录稳定的团队门禁结果，不能简单要求每次调用时全部仍为 ready |
| 观察与停滞 | 仅观察活跃 attempt；持续无有效进展后发状态请求；从实际请求时刻计算宽限 | 当前预算按时间差推导，无请求确认与阶段过滤 |
| 替换 | 旧操作确定停止、成果保全、角色预算未耗尽、没有已存在的新 attempt | 当前只返回基于 attempt 数字的计划，不检查停止证据或已存在替代者 |
| 接收完成 | 报告身份、分支 tip、SHA、范围、验证记录与停止证据一致 | 当前主要是协议要求，无统一代码入口 |
| 返工 | 报告审查不通过，形成新任务修订并保留旧报告与派发记录 | 当前 reported 无返工出边，dispatch 只接受 ready |
| 串行集成 | 分支已审查，tip/base/祖先关系核验通过，worker 静止，集成 checkout clean | 当前主要依赖 leader 按协议执行 |
| 归档 | 来源身份明确，按 role/attempt/修订保存；目标内容复制完成并校验 | 当前按 role/name 保存，替换报告会产生冲突 |
| 删除 worktree | 确认为本 run 的专用非 primary 资源；停止、clean、未合并成果、忽略文件保全等证据齐全 | 清理分类没有将这些证据合为删除前置条件 |
| 取消与中止 | 先禁止新派发；发停止请求；继续观察到实际停止；保全成果并单独推进清理 | 当前 worker 没有停止请求/等待停止的独立状态 |
| 完成运行 | 最终审查通过、清理完成、无未决异步资源；业务失败后仍需跟踪清理债务 | 转换校验和扫描没有强制这些跨字段条件 |

## 三、已发现的问题

优先级定义：P1 为接入自动执行前应先修复的正确性缺口；P2 为随后补齐的生命周期与维护问题。当前清理模块只生成计划，不直接删除，因此不能把错误计划描述为已经发生的数据损失。

### L01 · P1：正式派发可以绕过完整启动门禁

- 位置：`scripts/controller.py:48`、`scripts/controller.py:42`。
- 触发：目标 worker 为 ready 且有非空 threadId，省略 startup_report；即使另一 worker 仍为 pending、run 为 initializing，仍会发送消息。
- 复现：两个 worker 中 A ready、B pending，run initializing，调用 `dispatch('a', 1, 'probe')`，fake adapter 记录 1 条消息，A 变为 dispatched。
- 影响：代码无法强制 Skill 中“全部启动验证通过后才开始派发”的要求；非空 ID 本身也不能证明是真实 threadId。
- 建议：把门禁证据绑定到 run、role、attempt、仓库身份、基线及观察时间，校验后保存；派发校验 run 阶段、团队门禁、目标身份和集成 HEAD。支持从已保存证据派发，但不能仅相信 ready 标签。
- 验收：缺证据、他人证据、过期或不匹配证据、另一 worker 未初始化、集成漂移均零消息；A 派发后仍可正常派发 B。

### L02 · P1：消息发送与状态保存之间存在重复执行窗口

- 位置：`scripts/controller.py:61`。
- 触发：adapter 已成功发送，随后持久化失败或进程退出。
- 复现：注入 `write_state_atomic` 抛 OSError，观察到消息已发送，磁盘仍为 ready，内存为 dispatched。
- 影响：重启后仅凭磁盘状态可能再次发送同一任务；保存失败后内存也不再与磁盘一致。
- 建议：外部调用前持久化唯一 dispatch ID、任务摘要和发送意图；明确 sent/unknown/acknowledged 等结果；出现不确定结果时先核对 worker，不自动重发。内存变更与保存失败应有一致的处理规则。
- 边界：宿主若不支持幂等请求键，单靠本地状态无法保证消息严格恰好一次；应以可识别的任务 ID、确认和不确定状态阻塞控制重复风险。
- 验收：发送前、发送中、发送后保存分别注入失败；恢复后不得盲目重发，也不能将 unknown 宣称成功或失败。

### L03 · P1：恢复把未知误判为不存在，并对工作完成后的 HEAD 使用启动规则

- 位置：`scripts/recovery.py:9`。
- 触发一：worker pending、有 clientThreadId、没有真实 threadId，观察结果为空。
- 复现一：返回 `recreate`，没有先解析已有创建操作。
- 触发二：worker reported、线程 idle、分支正确、工作区 clean，但正常提交使 HEAD 不再等于 baseSha。
- 复现二：返回 `block`。
- 影响：前者可能引导重复创建；后者无法恢复正常已产出提交的 worker。
- 建议：外部观察使用 exists/missing/unknown 三态。pending 先解析，unknown 先重验；初始化阶段检查 HEAD == base，执行后检查 base 祖先关系、报告 SHA 与 branch tip。failed/cancelled 虽不可继续工作，仍应核对残留资源。
- 验收：pending 未决、查询失败、真实不存在、正常完成提交、范围不符提交分别得到不同动作。

### L04 · P1：清理动作没有受停止证据和资源归属共同约束

- 位置：`scripts/cleanup.py:8`、`scripts/cleanup.py:54`。
- 触发：传入工作树存在、worker idle/archived、已归档报告；即使没有完整停止证据，也能给出 remove。
- 复现：同一条计划返回 `worktree: remove` 与 `stop_evidence: unverified`。缺失 status_porcelain/unmerged_commits 也会被当作干净且无未合并成果；附带 primary 或非本 run 标记不影响结果。
- 影响：下游若仅执行动作字段，可能清理仍在使用或不属于本轮的资源。archived 不是停止证明。
- 建议：删除门禁统一检查明确的观察结果、归属、primary/shared、停止证据、Git 状态、未合并成果、忽略文件保全与报告哈希；任何未知返回保护原因。分支删除也需检查归属及是否仍被 checkout 使用。
- 验收：缺任一必需证据不能返回 remove/delete；只有完整确认的专用资源才可给出清理动作。本轮不新增真实自动删除。

### L05 · P1：结构化状态契约与控制器实际输出不一致

- 位置：`references/state.schema.json`、`scripts/controller.py:28`、`tests/state_schema_smoke.py`。
- 触发：调用 dispatch、write_plan 的降级路径，或创建超时处理。
- 复现：用现有测试中的 schema 子集校验器校验完整示例经控制器修改后的状态，分别得到 `unexpected dispatchAt`、`unexpected plan`、`unexpected lastCreateError`。
- 影响：真实状态接入 schema 校验会失败；当前 save 未校验，测试用的不完整 state 也能落盘。
- 建议：区分通用原子 JSON 写入与受校验的 run-state 存储；对 run-state 的读写强制版本、类型和领域不变量。统一计划、错误、派发、启动证据、模型配置与授权字段。校验 runId 与目录一致、role/attempt 唯一、complete 所需审查与清理条件。
- 补充：状态转换函数对任意同名旧/新状态直接通过，也未拒绝未知 kind；应先验证 kind 与状态成员，再判断幂等。
- 验收：使用完整 schema fixture 运行控制器；所有输出均合法，非法状态与跨字段冲突在任何宿主副作用之前拒绝。

### L06 · P1：原子写入和文件锁尚未组合成受保护的状态更新

- 位置：`scripts/state_store.py:68`、`scripts/state_store.py:140`、`scripts/controller.py:28`。
- 触发：两个控制器持有同一 run 的旧快照，分别更新不同 worker 并保存。
- 复现：控制器一将 A 改为 dispatched，控制器二将 B 改为 dispatched 后，磁盘变为 A ready、B dispatched，A 的变更丢失。
- 影响：文件内容没有写坏，但业务更新被覆盖；当前 StateLock 未被控制器使用。
- 建议：持有 run 排他锁执行“读最新状态→校验 revision→更新→持久化”；拒绝旧 revision。外部调用另用持久化意图协调，不能仅在保存瞬间加锁。
- 验收：真实多进程同 run 竞争、过期快照、异常释放、进程退出后恢复均有明确结果；不同 run 仍独立。

### L07 · P2：返工、停止请求与失败后的清理不是完整生命周期

- 位置：`scripts/state_store.py:14`、`scripts/state_store.py:133`、`scripts/controller.py:66`。
- 复现：`reported → running` 被拒绝，控制器也无正式返工入口；run aborted 且 cleanup pending，`latest_incomplete_run` 返回 None。
- 静态发现：replace_worker 对 ready worker 也返回替换计划，未核对停止证据、已有后续 attempt 或 state 中的授权上限；它仅生成计划，当前不会实际创建替代者。
- 建议：分别管理执行结果与资源清理结果；恢复扫描包含失败/中止后的清理债务和损坏状态警报。引入显式返工任务修订和停止请求/停止确认流程；替换预算从持久状态读取，并确保同角色仅一个有效 attempt。
- 验收：报告被退回后能正常返工；取消请求成功但线程仍 active 时禁止替换和删除；aborted 后未清理资源仍能被定位。

### L08 · P2：归档未按 attempt 与返工修订隔离

- 位置：`scripts/archival.py:37`。
- 复现：同 role 先归档 attempt 1 的 report.md，再归档内容不同的 attempt 2 同名报告，抛 ArchiveConflict。
- 影响：冲突拒绝保护了旧证据，但默认目录不能同时自然保存替换前后报告；返工后的报告也有同样问题。
- 静态发现：manifest 更新是未加锁的读改写，并发写入可能丢条目；复制前计算源哈希，复制过程非原子，未验证目标再提交 manifest。并发丢失与复制中断本轮尚未注入验证。
- 建议：使用 `reports/<role>/<attempt>/<revision>/` 与包含身份的 manifest 键；临时文件复制完成后校验目标，再原子发布；manifest 更新在锁内执行。
- 验收：不同 attempt/修订并存，同身份同内容幂等，同身份不同内容拒绝；并发、中途失败、来源变化均不会产生可误信的完整归档。

### L09 · P2：run 与归档目标缺少路径边界验证

- 位置：`scripts/state_store.py:92`、`scripts/archival.py:40`、`scripts/archival.py:48`。
- 复现：`run_state_path(root, '../escape')` 解析后落在 root/escape/state.json，超出 .threadweave；归档 role 为 ../outside 时，实际写入 run/outside/report.md，超出 reports 目录。
- 影响：API 输入错误就可能写到预期证据目录之外；schema 的 runId pattern 尚未在此入口执行。
- 建议：验证 runId/role/文件名为允许的单段标识；拒绝绝对路径和父目录段；对规范化目标以及符号链接做包含关系检查；校验 manifest 的目标同样位于预期归档根内。
- 验收：路径穿越、绝对路径、符号链接跳出均在写入之前拒绝，合法标识行为不变。

### L10 · P2：预算和停滞判断没有区分阶段与有效进展

- 位置：`scripts/budget.py:20`、`scripts/budget.py:52`。
- 复现：archived worker 在创建十分钟后仍被标为 initialization deadline_exceeded 与 stalled。
- 静态发现：summarize_budget 取出了 observations 但没有使用；lastObservation 混合“leader 看过”和“worker 有进展”两种含义；宽限按最后活动时间推导，没有记录状态请求真正发出的时间。
- 建议：区分 lastCheckedAt、lastProgressAt、statusRequestedAt、graceDeadline；只对适用阶段计算期限；八分钟后首次发现无活动时，先请求状态再给予完整宽限。长命令与依赖等待作为上下文，不能单凭 wait 超时替换。
- 验收：终端态不报停滞；无进展的反复查询不会刷新进展时间；请求未成功发送不能开始宽限；出现新进展取消旧停滞判定。

### L11 · P2：宿主适配接口尚不足以兑现创建超时与降级执行

- 位置：`scripts/controller.py:78`、`scripts/controller.py:91`、`scripts/host_adapter.py`、`scripts/project_resolver.py:13`。
- 新增代码的实际能力：fake adapter 验证了多/零项目拒绝、捕获 TimeoutError、可选工具返回降级标记；这些是有价值的本地验证。
- 复现：resolve_project 接受没有 projectId 的唯一记录，也接受 hostId 为其他主机的唯一记录。
- 静态发现：create_worker 的 timeout_seconds 未传入适配器，也未在控制器计时；因此是超时异常处理，尚不是主动 deadline。wait 降级返回模式描述，尚未执行带退避的观察循环；write_plan 可用时仅返回工具名。可选能力默认 True 未经实际探测。
- 建议：增加带 host 的项目解析与 ID 校验；定义结构化创建/错误结果、pending resolver、能力快照、等待 cursor 与可选停止能力。将“生成下一步计划”和“执行宿主调用”清楚分层；没有超时/取消能力时如实记录未知和限制。
- 验收：本地测试分别说明异常处理、超时调度、降级计划和真实降级；接入真实适配器后再补真实线程验证。

### L12 · P2：文档、恢复入口和测试对外契约需要统一

- 位置：`SKILL.md:88`、`references/leader-state-template.md`、`scripts/threadweave.py:49`、`docs/项目待办清单.md`、`docs/v0.1.0验收报告.md`。
- 静态发现：Skill 以 state.md 为权威记录，Python 扫描与教程使用 state.json；尚无同步规则。只按 Skill 创建 state.md 的运行不会被当前 JSON 扫描识别。
- 复现：state.json 为合法 JSON 数组时，locate_runs 抛 AttributeError；非 Git 目录的 CLI preflight 输出全部 false，但进程退出码为 0。
- 文档发现：待办仍保留“没有控制器”等早期描述，C4.3 又记录远端 CI 成功，C4.5 与验收报告仍写未关联远程。应明确历史快照与当前状态；本轮未联网重新验证发布事实。
- 建议：选定唯一机器状态源，Markdown 作为派生视图或明确保留纯 Skill 模式；新增 inspect/recover-plan/doctor 等只读诊断入口。明确 CLI 检查失败退出码与输入错误格式。将实现、本地验证、真实验证分别登记。
- 验收：仅 Skill 运行与辅助模块运行均有明确恢复方式；损坏/错类型状态可诊断；自动化可通过退出码识别 preflight 失败；测试不把期望行为固定成目前缺陷。

## 四、推荐推进顺序

### 第一批：补齐执行安全约束

处理 L01–L06，并先纳入 L09 的输入边界检查；为取消和替换加入保守的停止证据检查。

1. 统一 run-state schema 和领域不变量，建立受校验的存储入口。
2. 接入锁与 revision，解决旧快照覆盖。
3. 固化团队启动门禁与派发意图；对外部结果不确定的操作禁止自动重复。
4. 恢复与清理统一使用明确的观察结果，未知时保护资源。
5. 将本轮复现条件加入回归测试，重点验证“没有消息、没有重复创建、没有删除动作”。

完成标准：本地故障用例通过；原有正向流程保持可执行；仍保留宿主不支持能力的真实边界。

### 第二批：串起完整生命周期

处理 L07、L08、L10、L12：返工修订、停止确认、角色替换预算、按 attempt 归档、失败后的清理债务、CLI 诊断与文档一致性。先形成可审查的动作计划，再接执行。

完成标准：从创建前、派发后、报告后、集成后和中止后分别恢复，都能指出下一步以及禁止的动作；归档和清理均可重复执行而不损失证据。

### 第三批：宿主适配与 Codex 更新维护

处理 L11，并建立兼容维护流程：

- 每次运行记录宿主身份、观察到的版本、工具名称/参数结构、必需/可选能力、模型配置来源与证据日期。
- 保存规范化能力快照；更新后比较语义变化。必需能力不兼容则创建前阻塞，可选能力按已验证路径降级。
- 本地契约测试先行，再运行经用户授权的最小真实双 worker 冒烟与关键故障路径，最后更新兼容矩阵。
- 未验证的新版本明确标记待验证；不凭历史版本或版本号大小推断兼容。不把自动升级 Codex 作为本轮默认动作。

完成标准：可以明确回答“当前运行用了什么能力、哪些已验证、哪些发生变化、失败在哪一层”。

## 五、后续可衡量的优化

执行正确性收敛后，再记录初始化耗时、并行执行耗时、消息/读取次数、返工次数、合并冲突、清理残留和 leader 介入次数。成本与 token 只使用宿主实际可观察数据。

这些记录可用于判断哪些任务适合团队模式、worker 数量是否过多、哪些模板遗漏导致返工。多仓库、可视化与 PR 自动化继续作为待评估范围，本报告不将其纳入已授权实施。

## 六、本轮验证摘要

| 验证 | 结果与边界 |
| --- | --- |
| `python3 tests/run_all.py` | 最新基线 13 套、201 项断言通过；本地逻辑/fake adapter，不能替代真实 worker |

| 双控制器旧快照保存 | A 的 dispatched 更新被 B 的旧快照覆盖 |
| 替换报告归档 | 同 role 不同内容同名报告触发 ArchiveConflict |

| 恢复扫描与 CLI | aborted 清理债务被过滤；错类型 JSON 抛异常；preflight 全 false 仍退出 0 |
