# O11 失联识别与成果保全恢复验收记录

日期：2026-11-14。证据 Run：`20261114-o11-recovery-01`。

## 结论

O11 已按 A 路线完成“失联识别 + 旧成果保全 + replacement 授权”的 bounded 范围实现。没有新增含义模糊的 `lost` worker 状态；线程存在性使用独立观察字段和明确的确认证据区分。

当前实现不会把“线程查询失败或暂时不可见”直接当作不存在，也不会在线程确认不存在后直接删除旧 attempt。旧分支、HEAD、报告、notes、脏工作树补丁和 replacement 预算必须先有可验证证据。

## 线程存在性四态

| 状态 | 触发条件 | 恢复动作 |
| --- | --- | --- |
| `present` | `thread_exists=true` | 按 thread 状态、worktree、HEAD、报告和任务修订继续分类 |
| `unknown` | `thread_exists` 缺失或查询无结果 | `revalidate`，不得 recreate |
| `missing_unconfirmed` | `thread_exists=false` 但没有显式确认证据 | `revalidate`，要求 `thread_absence_confirmed` 和 evidence |
| `missing_confirmed` | `thread_exists=false` 且有确认证据 | 先检查旧成果保全，满足后才可 replacement |

## 成果保全门禁

确认线程缺失后，旧 attempt 至少需要以下证据：

- 旧 attempt、threadId、branch、完整 HEAD。
- `branch_preserved=true`，Controller 重新读取 branch ref 并与 HEAD 精确比较。
- `worktree_exists` 明确。
- 若 worktree 存在：`status_porcelain`、`unmerged_commits` 明确。
- 脏工作树必须提供补丁归档和 SHA256，不能直接丢弃。
- 旧报告/notes 若存在，必须分别归档。
- preservation record 由内容规范化哈希生成 `preservationSha`。

动作顺序：

1. 确认缺失但成果证据不足：`preserve_work`。
2. 成果证据齐全但尚未登记：`preserve_then_recreate`。
3. Controller 记录保全：`record_recovery_preservation`。
4. Controller 授权 replacement：`authorize_recovery_replacement`。
5. 只有授权后才能建议 `recreate`。

## Controller 行为

- `record_recovery_preservation` 不创建线程、不删除 worktree，只验证并持久化旧 attempt 保全记录。
- `authorize_recovery_replacement` 要求有效 `preservationSha`、旧 attempt/branch 匹配、没有后续 attempt、符合 replacement 上限。
- replacement 授权只允许下一 attempt 编号，不自动创建线程，也不构成发送消息授权。
- `recoveryPreservation` 和 `recoveryReplacementAuthorization` 是可选 schema 字段，旧状态继续可读。
