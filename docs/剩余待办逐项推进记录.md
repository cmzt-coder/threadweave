## O16 功能节点

- `DesktopLifecycleBridgeAdapter.list_artifacts()`：只查询当前调用者附件，经过 prepare → claim → 原始结果导入，不接受伪造目标 threadId 参数。
- `recheck_managed_cleanup`：同 run/role/attempt/taskRevision、0–30 秒宿主观察；等待必须精确命中目标且 idle/completed/final 同 turn；附件必须精确匹配资源身份，显式证明 ownerThreadId、runId、非 primary、非 shared；最后重新核对本地 Git 精确计划。
- 所有权字段未暴露、资源未列出、notLoaded/active、停止证据缺失或计划漂移时 blocked。
- `execute_managed_cleanup`：显式授权且重验 eligible 后调用适配器 archive_worktree；最终删除结果仍需宿主完成和资源复核。失败或未决不执行本地 Git 回退，不尝试绕过宿主限制。

原生工具实测：附件列表为空；对此前已归档聊天的 wait 返回 notLoaded，不能当作新鲜 idle。真实回执通过新增生命周期账本导入后，清理门禁返回 `worker not freshly confirmed stopped`，archive 未调用。本次证明安全拒绝，不证明宿主所有权字段可用或正向归档闭环。

宿主附件的 payload 结构不能凭空推断；本模块要求的所有权字段是放行条件，**不声称当前宿主提供这些字段**。当前查询只有调用者范围，无法读取任意 worker 的附件；这是仍待宿主能力支持的边界。

## H01 功能节点

- `prepare_handoff_intent` 在真实迁移调用前保存 pending、operationBound=false。此时即使进程退出，重载后也不能派发。
- `bind_handoff_operation` 仅对未绑定意图接受真实 operationId，禁止更换 model/thinking/head；目标身份/root/branch 在明确后绑定。
- 未决意图不能覆盖；重复绑定拒绝；保存失败回滚内存。
- operationBound=false 时任何回执都不能通过门禁。宿主拒绝或结果未知时保持未决，不盲目重试。

本轮补齐的是 Controller 本地意图接口及测试，原生 handoff 仍由 leader 在持久化后执行；没有后台自动调用，也未新增真实迁移。目标模型/附件只读证据仍缺，因此 H01 继续部分完成。

## O16 来源映射与宿主字段适配（2026-11-16）

历史真实原始回执发现并确认两个结构事实：活动/归档附件使用 `attachmentType`，且实际 payload 不含 ownerThreadId、runId、isPrimary、isShared 或 callingThreadId。此前只查 `type` 会导致真实附件识别失败；现由 `normalize_artifacts` 严格兼容 `attachmentType`/旧 `type`，冲突即拒绝，并继续要求原清理门禁中的所有权、保护、停止和 Git 证据。

新增 `scripts/resource_provenance.py` 只读映射器。它从项目账本取得 runId/role/attempt/taskRevision，再核对创建与附件操作的状态、绑定、request/response 哈希、原始回执文件、sourceRoot、目标路径、版本前进和 0–30 秒时效。输出只可能是 `associated`/`associated_archived`，固定保留四项未知字段并强制 `cleanupEligible=false`、`deletionPerformed=false`。

支持范围仅限历史实证的同步 `type=created` 回执；pending/queued/未知格式不猜测。映射尚未接入删除授权，因此不能据此解除 managed cleanup 对宿主 payload runId/owner/保护字段的要求。
