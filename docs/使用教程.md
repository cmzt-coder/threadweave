# Threadweave 使用教程

本文面向第一次使用 Threadweave 的用户，覆盖前置条件、安装、第一次运行、常见问题与恢复清理。

## 一、前置条件

Threadweave 依赖 Codex 的真实线程能力，不是普通 subagent 编排。使用前请确认：

- Codex 客户端支持 `create_thread`、`send_message_to_thread`、`read_thread`、`list_projects`、`wait_threads`。
- 支持独立 worktree 与 Git 操作。
- 目标仓库已登记为 Codex 项目，且 `list_projects` 能按仓库根目录唯一匹配。
- 当前任务允许你明确请求创建 worker 线程（部分宿主会把当前任务的委派限制为 subagent）。

如果缺少上述能力，Skill 会停止并说明原因；不要用 subagent 冒充真实 worker。

## 二、安装

```bash
git clone https://github.com/cmzt-coder/threadweave.git \
  "${CODEX_HOME:-$HOME/.codex}/skills/threadweave"
```

安装后重启 Codex，让 Skill 生效。

## 三、第一次运行

1. 在 Codex 中打开目标仓库。
2. 把目标仓库登记为 Codex 项目，确保 `list_projects` 返回的 `path` 等于仓库根目录，且 `isGitRepository: true`。
3. 发起任务，说明需要几个 worker、各自负责什么、如何验证：

```text
用 $threadweave 把这个任务拆给两个 worker：
- worker A 负责 <范围 A>
- worker B 负责 <范围 B>
各自使用独立 worktree 和分支，完成后串行集成并运行测试。
```

4. leader 会先做 preflight、创建 worker、验证启动报告，全部 ready 后才派发任务。
5. 完成后检查最终报告、合并结果和清理状态。

## 四、项目登记与 projectId

Threadweave 要求 `list_projects` 唯一匹配目标仓库根目录。

常见错误：

- 只登记了父目录（非 Git 项目）→ 不能复用其 projectId。
- 把文件路径直接填入 projectId → 协议会拒绝。
- 多个项目匹配同一仓库 → 视为歧义，阻塞创建。

正确做法：把目标仓库根目录本身登记为独立 Codex 项目。

## 五、本地辅助命令

项目自带一个只做本地检查的 CLI，不调用宿主 API：

```bash
python3 scripts/threadweave.py preflight --repo .
python3 scripts/threadweave.py status --repo .
python3 scripts/threadweave.py cleanup-plan --repo . --run <run-id> --observations <file>
```

- `preflight`：检查仓库是否 attached、有提交、工作区干净。
- `status`：列出 `.threadweave/` 下的 run，返回最近未完成 run。
- `cleanup-plan`：读取状态与观察，输出清理计划；不执行删除。

## 六、常见问题与故障排查

### `create_thread` 被宿主限制

部分宿主禁止在当前任务中用 `create_thread` 委派子任务。此时需要：

- 在用户明确发起的新任务/新会话中运行；或
- 换一个允许真实 thread tools 的宿主。

不要用 `spawn_agent`/subagent 冒充真实 worker。

### `list_projects` 没有匹配

说明目标仓库没有作为独立 Git 项目登记。请把仓库根目录登记为 Codex 项目，不要复用父目录 projectId。

### worker 启动验证失败

检查 worker 报告的实际：

- cwd 是否位于其 worktree root 内；
- Git common dir 是否与 leader 一致；
- 分支是否等于分配的分支；
- HEAD 是否精确等于 base SHA；
- 工作区是否干净；
- worker root 是否与 leader/其他 worker 重叠。

任一不满足，leader 会拒绝派发，不会自动重置或覆盖。

### 取消或停滞

- 取消通常是 turn 边界 steering，不保证立即中断当前命令。
- 需要等待 turn 结束、线程 idle，并核对停止证据与已保存成果。
- 超过 6 分钟无活动，leader 会请求状态；再过 2 分钟宽限仍无活动，才判定停滞。

### 模型不可用

显式指定的模型/reasoning 不可用时，创建会在派发前失败，不会静默替换为其他模型。

## 七、状态、恢复与清理

- 状态目录：`.threadweave/<run-id>/`，已被 `.gitignore` 忽略。
- 结构化状态：`state.json`；报告与 notes：`reports/<role>/`。
- 恢复分类：`scripts/recovery.py` 会给出 `skip/recreate/block/revalidate/reuse` 动作。
- 清理前会检查：worktree 是否干净、分支是否已合并、报告是否已归档、worker 是否 idle。
- 不要强删活动 primary checkout；先把线程切回 Local，再执行非强制 `git worktree remove`。

## 八、权限与安全

- 创建线程、worktree、发送消息、提交、集成、推送都需要用户明确授权。
- 默认只提交、不推送；推送需要用户明确要求。
- `.threadweave/`、`.DS_Store` 等运行时/本地文件不应提交。
- 不要把 token、密钥、`.env` 或内部路径写入公开文档。

## 九、限制

- 需要真实 thread tools；不支持 subagent 冒充。
- 部分故障路径仍在受控环境中验证中，详见 `docs/宿主兼容矩阵.md` 与 `docs/第一轮执行闭环验证记录.md`。
- 当前版本是 `0.1.0`，接口与协议可能继续演进。
